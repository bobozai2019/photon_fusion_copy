## 会话和模板身份

原生入口复用 TCP provider 与 Core 房间。Control 载荷包含房间和轮次标识。双方用原生版本 5 与模板目录指纹协商能力。版本 2 增加 RPC 写权代次、写者身份和原生房间人数。版本 3 将人数扩展为名单，在 RPC 投递中携带原始目标，并增加房间广播与节点引用参数。版本 4 增加 RPC 请求的发送端处理标记和输入指令的逐条 delta。版本 5 启用按 delta 消费和房主同步输入，模型签名会区分原来的固定消费。指纹包括模板顺序、资源路径、字段布局、写权模式、兴趣和模型选项。模板身份是有序目录索引，字段身份使用复制布局。同一布局上的不同场景用各自目录项实例化。

房间属性首份快照完成后发入房信号。房主关闭声明了不匹配版本或目录的连接，并在八秒后关闭始终未协商的席位。房间快照包含已完成原生协商的玩家名单。客端按收到的名单变化逐个发出信号，所以暂停一帧时积压的加入和离开仍可分别观察。另一种选择是每帧比较最终名单，暂停观察客户端并让第三人完成进出可以区分两种行为。客端生成还需房主确认其 Core 基线与写权模型可用。

Fusion Racing 和官方接入示例在入房时直接生成并访问车辆。客端在 `room_joined` 可以同步取得本地节点，Core 就绪后发送原请求。客端的待发送和待确认实例合计上限为 64。生成握手与正式写权仍有各自的就绪条件。发送前取消只回收本地节点。发送后用创建引用回收。用每方向 35 ms 延迟验证入房回调、首值、取消和离房。[官方接入示例](https://doc.photonengine.com/fusion-godot/v3-shared-authority/manual/csharp-bindings#quick-start-guide-example)

房主原子处理属性补丁。删除操作在线上用零长度记录表示，Godot 的 `null` 作为正常值保留。CAS 检查现有键和预期值，并在应用整批补丁前比较 Godot 值。可区分的替代方案是比较序列化字节，重排预期字典的键顺序即可验证这一差异。

生成请求复用连接分配的创建命名空间与递增序号。房主以模板决定布局、复制范围和权威模式。字段按布局解码并在创建时整批校验。同一请求的重发返回原结果，客户端按所属命名空间匹配暂存节点。网络身份的高字存放模板目录项，低字由房主分配。超时与取消请求都按原创建引用回收。

旧脚本入口保留原来的协议消息和行为。使用旧版 SDK 的房主能完成旧入房流程，缺少原生版本回应的客端在协商超时后报告失败。

## 对象调用与预测

原生 RPC 以 Core 当前写者决定 Owner 路由。对象投递确认发送端及接收端的可见范围，房间广播按原生协商名单投递。接收端只调用匹配 `@rpc` 的方法或列在 `rpc_methods` 中且由目标脚本声明的方法。广播接收者各自解析节点引用和容器参数。插件目标留给后续服务端处理器。

Fusion 的本地 RPC 在发起调用返回前执行。v4 在请求受理后立即执行选中发送端的 `call_local`，并让房主从投递列表移除实际发送者。若沿用房主回送方案，只能在下一次会话推进时看到本地效果。Shared 测试在方法返回时读取回调计数，并在回执后再次读取以区分两种做法。客端的 Owner 路由仍通过房主核验代次，避免在收回写权的消息途中执行旧调度。同代次 Owner 的基线尚未就绪时继续等待。

Transaction 按当前写端的同步回调投票。任一 `true` 即批准，有布尔票且全部为 `false` 时拒绝。同步回调也可以显式答复，后续布尔票不会覆盖该答复。Deferred 回调仍可显式答复。房主参与常规请求时使用同一个待批准状态，管理员收权是独立入口。可区分的替代方案是房主直接替换当前写者。让客端持有写权并拒绝房主请求可验证这一点。

Owner 请求与投递同时携带写权代次。房主拒绝跨代次路由，收件端在同代次基线就绪后执行。另一种选择是在就绪前立即返回失败，由玩法重试。Shared 测试在房主收回写权当帧提交一次 RPC 并要求只执行一次，区分这两种行为。带 `@rpc` 注解的收件端用房主路由时的写者快照校验发送方。

输入模型由 Core 维护预测历史和消费序号。Godot 适配层在每个模型步先应用传入字段，再执行业务回调并采样。重演与首次执行使用同一回调，`is_new` 区分重演。普通字段通过现有采样和应用逻辑处理，刚体 Auto 由旧物理适配器继续负责。

有输入模型的原生会话用 16 ms 的固定服务步提供每秒 62.5 个消费机会，覆盖默认 60 Hz 的生产速率。另一种选择是在 30 ms 步内消费多条积压输入，同时为每条分别推进玩法状态。持续输入测试以 60 Hz 提交 360 条，检查总确认号、累计状态、队列峰值与回调步长。

输入指令使用四字节 float 保存调用者传入的 delta，后面是原业务 payload。预测历史保存完整指令，权威端和重演解出同一 delta。v4 仍每步最多消费一条。Fusion Preview 555 的原生证据显示，处理远端输入时 Master 按队首 delta 累计时间，Master 本机则直接分派。v5 在房间服务步上累计可用时间，并允许本机输入同步提交。旧 Core 模型仍按每服务步一条消费。[555 输入证据](../../research/fusion/findings/native-runtime.md#client-server-的输入发送消费和重演)

带时间输入的模型 tick 独立于网络服务 tick。多个命令在一次网络服务步执行时各自推进一次模型 tick，权威样本仍按当前网络时钟发布。已同步执行的本机时间抵扣后续服务步，包括一次追赶多个步长的情况。改授输入权后，旧积压和累计时间随旧代次清除，模型 tick 不回退。迁移检查点保存模型 tick 和本机已提交但尚未抵扣的时长，后继房主继承旧房主输入权时可继续抵扣。每条指令最多一秒，避免超长队首长期阻住对象。可区分的替代方案是继续固定每步消费一条，只把 delta 传给游戏回调。Core 手动时钟用例连续提交 48 ms、8 ms、8 ms 三条指令，并检查头两步不执行，第三步执行队首，第四步连续执行后两条。同一用例还检查房主本机输入在网络时钟未推进时已提交，之后不会重复执行。
