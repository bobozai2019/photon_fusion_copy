为什么要保存步号、已结算输入和有符号车速？

步号回答“哪一刻”。 客端用房主的时间样本估计模拟步，把输入标记给预计能抵达的目标步。每步锁存一次输入，发包时可捎带最近几步。同一目标步只结算一次，已过截止的输入按缺失规则处理。

确认回答“算到了哪里”。 对象版本确认表示对端收到了某次属性变化。预测还需要房主报告该驾驶者已结算到哪个输入步，即使车顶着墙没动，也要推进这项确认。

速度回答“下一步会怎样”。 同一位置上，一辆车已停住，另一辆还在滑行。只恢复位置，两车下一步就再次分开。历史应包含真正送入模拟的输入、步末状态和当时的碰撞环境。

位置、速度和控制器状态在容差内，离散状态吻合。推进输入确认并保留 T 之后的预测。

↳ 历史齐全 · 超差恢复 T，从 T+1 重演

恢复步末的位姿和速度，用原输入、当时的环境算到预测头。覆盖旧历史，这轮重演跳过已包含在检查点内的 T。

↳ 必需历史缺失取得完整基线

先呈现权威结果。拿到当前车辆与碰撞世界后，从基线之后恢复预测。跨局、旧授权的迟包直接丢弃。

碰撞体与显示模型

重演结束就提交新的碰撞位置。显示模型可暂留上一可见位置和新结果之间的偏移，再逐帧衰减；传送时清除偏移。重演中的碰撞音、RPC 和计分要抑制或去重。

远车插值与有限外推

C 略晚播放权威轨迹。在第 100 步 x=10 与第 103 步 x=13 之间，播放到 101.5 时线性插值得 11.5。缓冲耗尽可短时按速度外推，接触、传送或超时后停止。

重建当时的碰撞环境

若门在 105 步开启，重演 103 步仍应关着门。两辆车互相施力时，要用同一个 T 恢复相关刚体，或让房主统一裁决。延迟播放的远车只适合显示。

04落到三个引擎

核心统一步号、输入、历史与确认。各平台在自己的物理安全点绑定刚体、采集或恢复状态，在渲染阶段写显示模型。

车场已实现的行为

每款引擎分别在自己的房间运行车场。房主按 30 Hz 结算车辆，客人的本车按输入预测，收到权威检查点后重演未确认输入，远车按约 100 ms 延迟插值。车场也已验证按对象交接写权。上方实验数值来自车辆运动公式的教学推演。

Unity

共用模型预测自车，C# 主线程处理绑定和呈现。原生路径可用独立 PhysicsScene 或 PhysicsScene2D 手动固定步进，确保同一世界只有一个驱动者。

Godot

共用模型可以逐步回放。原生刚体在物理安全点采集与纠偏；项目采用的 godot-cpp 4.5 公共绑定未提供等价的独立世界单步入口。

Cocos2d-x

当前构建关闭原生 2D 和 3D 物理，先复用 C++ 车场模型。原生扩展分别接入 Chipmunk 或 Bullet，并分别验证场景和后端的步数。

这些机制怎样对应 UE 与 Fusion？

UE 的 Resimulation 会把权威物理帧与本地同帧历史比较，超差时恢复并补演。Fusion 2.1 的 Physics Addon 可在正向与重演 tick 驱动场景；Godot Shared 的刚体 Forecast 用最近的速度估计远端运动。上面的自车实验对应前两者的回放原理，旁观者的有限外推对应后者的用途。原版适用的拓扑和资料见设计依据。
