# 通用对象同步与客户端状态权威

一个玩家房间可同时容纳房主写入和指定客户端写入的对象。应用按对象分配写权。同一客户端可以写手里的协作拼图，同时观察计分板，并给另一对象提供控制输入。房主运行于普通玩家进程，负责成员身份、授权和发布已接纳的状态。拼图和车场共用 [ObjectAuthority](../../core/session/object_authority.hpp)。

## Fusion 的时间与状态策略

| 问题 | Fusion 3 的依据 | 本框架的选择 |
| --- | --- | --- |
| 游戏进度怎样推进 | Core 在 `UpdateFrameBegin(dt)` 推进网络时钟并处理收包，宿主运行游戏逻辑后调用 `UpdateFrameEnd()`。`GetSendTick()` 表示发送状态包的计数，对象的 `GetTime()` 表示权威产生该状态的网络时间。 | 将模拟步、对象来源序号、状态版本、发包序号和渲染时间分开。可预测模型采用协商的固定步，事件驱动模型可以按编辑或状态变化序号更新。30 Hz 模拟和 20 Hz 发包属于当前车场配置。[Fusion 帧循环](https://doc.photonengine.com/fusion-core/v3/manual/frame-loop) · [Fusion 时间模型](https://doc.photonengine.com/fusion-core/v3/manual/time) |
| 怎样知道应当重演哪些输入 | Client-Host 的 `PlayerPredicted` 对象指定输入玩家，保存带序号、时长和业务载荷的输入。权威状态带已消费输入位置，预测端清理已确认项，在下一次执行输入队列时触发重置并重演剩余输入。555 双端实测中，Host 对 60 个不同输入各执行一次，一轮预测端有 26 次重置和 416 次重复输入回调。 | 只有启用预测的模型才需输入历史、同一步的权威检查点和已结算输入序号。状态包 ACK 继续表示复制进度。可靠的一次性行为在重演时避免重复执行。[Fusion 输入权威](https://doc.photonengine.com/fusion-core/v3/manual/ownership) · [555 客户端实测](../../research/fusion/findings/client-audit.md) |
| 完整状态保存什么 | Godot 的 AUTO 刚体组件可同步姿态、线速度和角速度，代理以这些值做 Forecast。Racing 的控制轴和模型朝向由样例另行声明。Shared 允许持权玩家写对象。自定义控制器的私有积分量由应用决定是否复制。 | 模型声明公开状态以及继续模拟所需的恢复数据。移动控制器可增加有符号速度，回合计时器可增加截止时间，拼图可以只需格位和朝向。两个位置相同但内部速度不同的实例，必须能在恢复后得到各自正确的后续结果。[Fusion 刚体复制](https://doc.photonengine.com/fusion-godot/v3-shared-authority/manual/physics-replication) · [随包源码](../../research/fusion/findings/sample-scripts.md) |

Fusion 的 Shared 与 Client-Host 是不同的会话模式。这里选用本项目的玩家房主分发拓扑，在同一局支持不同对象采用不同策略。客户端提交自己授权范围内的最终状态，房主核验并分配公开版本。旁观者从公开版本恢复。普通回显只确认进度，持权者可以继续本地编辑或模拟。[Fusion 官方拓扑](https://doc.photonengine.com/fusion-core/v3/getting-started/modes-and-topologies)

## 哪个端可以做什么

| 职责 | 生命周期和权限 |
| --- | --- |
| 房间协调者 | 将真实连接映射到玩家，决定对象身份、生成和全局销毁、授予或回收写权、验证并分发状态。普通直连会话随房主退出结束；启用热备时按[接替协议](game-session.md#玩家接替房主与本地找房)恢复已保存的检查点。 |
| 状态写入者 | 每个可委托对象在一个授权代次内有一个写入者，可为房主或选定客户端。模板声明可提交的状态字段。其余字段继续服从房主的业务规则。不同玩家可同时写不同对象。 |
| 输入提供者 | 向采用输入驱动的模型提交意图。该玩家可以本地预测，房主或状态权威仍可裁定结果。事件驱动模型可以完全没有输入流。 |
| 业务归属和 RPC | 按业务归属登记的方法使用 `Object.owner`，按状态写者登记的对象方法跟随当前写者和授权代次。生成、计分和背包结算仍服从各自的玩法权限。[方法作用域与方向](rpc.md#命名方法与参数契约) |
| 观察者 | 应用已确认状态，依据模型选择立即呈现、缓冲插值或有限外推。可向业务层申请写权，只有授予消息和基线到齐后才能成功提交。 |

例子：房主 A 将拼图 X 授给 B、拼图 Y 授给 C。B 可提交 X 的格位，C 可提交 Y 的格位。两人都只能向房主发起“提交答案”命令。倒计时由房主写截止时间，各端用网络时钟显示。角色移动可以单独启用输入预测。物体的所有权变化不要求全房切换模式。

## 框架边界与接入契约

这里的“模型”是一类游戏对象的状态和更新规则。例如协作拼图在玩家操作时改变格位及朝向，角色运动则根据输入、当前位置及速度推进一个模拟步。“运行时代码”是游戏启动后实际运行的程序，负责把 B 对拼图的操作传到 A 和 C，并在换权后拒绝 B 的旧操作。验收分别检查设计契约以及程序真正产生的跨端结果。

| 位置 | 框架提供 | 应用或引擎提供 |
| --- | --- | --- |
| `core/state` | 稳定的对象和 schema 身份、版本化字段、差量、基线和各接收者的确认进度。扩展字段类型时同步扩展编码、校验和容量声明。 | 应用声明哪些字段应复制、可交接、可插值以及模型版本。布尔状态可立即应用，姿态和离散枚举可选不同呈现方式。 |
| `core/session` | 维护每对象的写入者与授权代次。将入站连接解析为真实玩家，核对对象、代次、变化顺序、字段范围和模型校验，接纳后调用常规复制入口发布。提供授权变化、可提交状态、已接受、恢复基线和失去写权等通知。 | 应用决定哪些玩家有资格获得哪些对象，接管时继续模拟还是冻结，以及哪些状态转移合乎玩法。 |
| 模型和预测扩展 | 宿主按各自的时钟接入网络收包、模拟以及发包。预测扩展负责保存和裁剪输入、按权威检查点恢复及重演。 | 模型提供采集与应用。可预测模型额外提供保存、恢复和单步逻辑。原生刚体另外声明可隔离单步与成组恢复的能力。 |
| `engineplatform` | 把框架对象和字段绑定到各引擎实例，管理挂载、销毁和句柄失效，并选择本地呈现源。 | Unity、Godot 和 Cocos2d-x 各自在适当的线程和生命周期访问引擎对象。车辆运动、拼图格位、背包和胜负条件留在模型或样例。 |

业务侧的最小调用顺序是注册模板与字段，生成对象，房主授予指定玩家，持权方提交新状态，其他端接收对象变化。应用可查询当前写入者和授权代次，也可选择把对象收回房主管理。输入预测是同一套对象身份、时间和状态复制之上的另一项能力，授予客户端写权可以独立交付。[已有状态层](../../core/state/replication.hpp) · [已有 RPC 层](../../core/session/rpc.hpp)

| 业务操作 | 输入与结果 |
| --- | --- |
| `register_model` | 开局前注册模板、模型版本、按 ID 升序排列的可写字段、恢复数据上限和可选的业务校验。双方通过同一协议版本和模型签名协商兼容性。 |
| `assign` | 房主指定对象和新写入者，传入房主步号以及交接所需的恢复数据。转出方为客人时保留其最后接纳的模拟步和恢复数据。重复指定当前写入者时直接成功，维持原代次。 |
| `writer` / `grant` | 查询写入者、代次、基线和该代确认进度。从未委托的对象默认由房主写。收到授权后，客户端提交仍要求本地对象存在且模型匹配。 |
| `submit` | 客户端传入对象、代次、可选模拟步、完整的可委托字段值及恢复数据。会话层分配代内序号并更新本地视图，下一次发送步上行最新待确认状态。布尔与有限浮点沿用复制编码。 |
| `Changed` / `presentation` / `forget` | 换权且对象就绪后通知应用。呈现使用本地持权值或公开状态，必要时用交接基线填补快照间隔。销毁时适配器清除授权和呈现缓存，对象 ID 在同一局内不可复用。 |

## 交接、乱序与恢复

1. 房主在可靠路径发布对象、写入玩家、新代次、来源进度和可独立恢复的交接基线。初始没有委托的对象由房主写。再次收到相同代次的授权不会重新应用旧基线。
2. 客户端上报带对象、代次、来源序号以及模板允许字段的状态。房主用连接核对写入者，检查会话与局次、对象存活、字段类型和范围、模型版本与更新顺序。未通过的状态不能产生公开版本或触发业务事件。对象可见和拥有写权分别判断。
3. 换权时先封闭旧代次，选择最后接纳状态作为交接点。旧写入者仍可能短暂显示本地操作，房间只承认当前代次。断线后房主接管或按模板冻结，重连客户端先取新基线，再根据业务策略取得新授权。对象销毁或换局应清理旧授权、队列和历史。
4. 数据复制的 ACK 确认公开状态版本，客户端提交确认携带该代次已接纳的来源序号。预测模型的已处理输入序号独立传达。历史不足时，以完整权威基线恢复。房主接管动态对象需要拿到足够的模型恢复数据。
5. 同一字段只保留一个状态写入方。多对象原子事务（例如道具交换）由应用指定的共同权威执行，再发布结果。可独立委托的状态边界应与玩法需要的一致性边界匹配。

房主接入时从房间成员表绑定真实连接，再确认客户端已收到复制基线。房主的业务模拟在委托期间跳过可委托字段，可以继续采集其余字段。会话层用最新公开对象合并来包。旧连接、旧局、旧代次、错误字段编码与重复提交都无法改变公开状态。业务校验拒绝新状态时，房主收回写权并发布最后接纳的基线。尚未协商或模型签名不兼容的客人继续使用公开复制，不能获得该模型写权。RPC 持续通过 `Object.owner` 进行既有检查。

控制通道传送能力协商与授权。状态上行、接纳确认、公开快照及快照确认使用游戏通道。授权包本身含可委托字段与恢复数据，公开版本继续用于复制确认。若控制消息先于对象到达，接收端保存授权直至对象出现。已销毁对象的迟到授权不会恢复其生命周期。

协商 word 差量后，授权内的 `AuthorityStateWords` 只携带该样本尚未确认的可写 word，并继续携带源步和恢复数据。房主以同一代次最近接纳的样本为基准合并，完整重建候选样本后再执行业务校验。`AuthorityAck` 仍确认已接纳的样本序号。只有恢复数据或源步改变时，允许零个变更 word。[差量与写权实现](../../core/session/object_authority.cpp)

可靠有序的 Game 通道可额外协商 `AuthorityBatchHello` 和 `AuthorityBatchSupported`。由客机发起，每个连接和回合各自协商，协商前沿用单条状态及确认。协商完成后，客机在本次发送循环内把待发状态装进 `AuthorityStateBatch`，同一包可以混合逐 word 和全字段记录。每条记录以一个 16 位长度字开始，最高位表示逐 word，其余位表示记录长度。房主先检查整包边界，再逐条校验对象、写权代次、序号和字段。每个包的确认用一条 `AuthorityAckBatch` 返回，按对象、代次和序号三元组结算。状态包及确认包均遵守 Game 通道的 1176 字节上限。再次提交仍依据各对象最近确认的序号。[线上消息编号](../../core/session/game_wire.hpp) · [实现与校验](../../core/session/object_authority.cpp)

房主发送 `AuthorityGrant` 时，为该接收方登记授权引用的对象版本。若该版本尚未确认，房主用完整字段刷新并按连接重试。即使两次采样间的值变回原样，或者观察者较晚完成模型协商，公开副本仍能追到授权引用的版本。场景和依赖的可见性条件照常生效。[授权投递](../../core/session/object_authority.cpp) · [基线选择](../../core/state/replication.cpp)

## 场景、依赖与可见集合

`AuthorityState::set_interest(peer, scene, selected)` 由房主为每位玩家指定场景和可见对象。玩法可以按队伍、区域或任务生成集合。场景 0 的对象跨场景可见，空订阅集合表示看不到任何对象，省略集合表示接收所有匹配对象。进入视野送当前完整状态，离开视野发隐藏通知，销毁永久封闭本局内该身份。可选依赖最多 16 项，使用先已创建的对象身份。房主等前置对象确认后发送依赖它的对象，客端按依赖顺序在 `AppliedSnapshot::ready` 发布就绪。客户端持权对象离开该玩家的可见集合时房主停止接受其提交并可接管。[复制接口](../../core/state/replication.hpp) · [乱序重入与销毁测试](../../tests/core/interest_test.cpp)

销毁前置对象后，依赖它的对象保留在房主状态中，所有观察者停止看到该对象。前置对象身份在本局不可复用，检查点保留依赖边及隐藏行为。房主可按玩法需要显式销毁依赖者。

## 本版验收

| 用例 | 通过条件 |
| --- | --- |
| 通用性 | 无引擎测试用同一接口注册两个结构不同的对象。至少一个是没有物理位姿、速度和固定模拟步的离散对象。新增模型只增加 schema、规则和适配，不增加 Core 的玩法分支。 |
| 真正的客户端权威 | A 为房主，B 获得对象 X 的写权，C 旁观。暂停 A 对 X 的业务模拟，B 只发状态，A 与 C 仍能看到 B 的操作。保持另一个对象由 A 或 C 写，B 对它的提交无效。 |
| 交接与断线 | B 写入后转交给 C，重发 B 的旧更新和过期授权。所有端最终读到 C 的新状态。丢失、重复、乱序、重连和换局下，过期写入均不再生效。 |
| 连续模型 | 固定 30 Hz 模拟，以 10 Hz、40 Hz 发送运行。对同一位置分别提交正负速度，收回写权后在房主侧沿对应方向继续运动。 |
| 接入和容量 | 核心可独立构建。三种引擎通过同一授权契约，各自在本引擎完成双端验收。用已有四人百对象作为回归负载，另测委托对象数、状态上行量、交接延迟与内存。 |

房主迁移、跨地域匹配、全场景原生物理回滚有各自的前置条件。可移植的对象写权、状态复制、引擎绑定和两类模型验证构成本版框架的首个交付边界。[项目验收基线](../../task/cross-engine-sync/验收/M6.md)

资源异步加载时，适配器可先调用 `ReplicaState::set_scene_ready(scene, false)`。完成加载后调用同一接口并传入 `true`，从返回的 `ready` 列表按序创建或激活实例。期间到达的快照继续更新暂存值。房主对某玩家的可见集合进行切换时，其他玩家已确认且未变化的对象无需重发。[场景与依赖就绪](../../core/state/replication.cpp)
