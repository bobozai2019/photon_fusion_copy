# Godot 纯属性双端同步实测

本文的采样次数、字段格式和时序属于 2026-11-22 实测的 Godot 插件。源码链接用于定位兼容脚本和 Core 中对应的处理位置；现行原生节点的采集、逐 word 检测和代理应用见[运行时架构](../../../docs/architecture.md)。

2026-11-22。在一台 Intel i5-9300H（4 核 8 线程）Windows 机器上运行两个真实客户端，一人持有所有对象，另一人看见全部对象。自研路径是 Godot 4.7.1、Release 安装版插件（DLL SHA-256 前缀 `f6a81be7db7638bc`）和本机回环。Fusion 路径是 Racing 3.0.0 的 Preview 555 原版 Web 扩展和模板、两个 Chrome 客户端、Photon Cloud Asia 房间。普通 Node3D 只配置整数属性，场景没有物理体、碰撞、变换复制和 RPC。测试脚本共用同一套生成值、负载与终值校验。[复现命令](../probes/README.md#纯属性数量与变更比例) · [测量实现](../probes/property_scale.py)

## 指标

- 默认每对象声明 20 个独立属性。50 至 250 个对象对应 1,000 至 5,000 个属性。另将对象数固定为 250，在每个对象上配置 4、12、20 个属性，以观察对象数和属性数的影响。单对象 5,000 字段与此测试属于不同布局；自研 Core 注册的单对象模板最多 64 字段，另受单个记录的最大编码长度约束。[注册检查](../../../core/state/replication.cpp#L59)
- 双方先逐字段核对唯一的基线值。写端按墙钟每 100 ms 发起一轮，共 60 轮；每次回调最多执行一轮。全量时每轮改所有字段；稀疏时按字段序号轮换改 10%，每字段总计改六次。每次写入可逆混合字段身份和版本，字段间拥有不同值。
- **写入期间可见变化/秒**统计远端在写端停写时刻之前应用的不同字段版本，除以写端整个测量时长。观察端每个引擎步对应用时间合并计时，临界值的分辨率约为一个观察步。**累计版本可见率**为停写并等待后，观察端曾见过的不同字段版本数除以写入总数。两项衡量应用层状态变化。包数、线上字节和丢包率需要单独测量。
- **尾部等待**从写端最后一轮写完算起，到远端全部收到各字段各自的目标版本为止，使用同机墙钟。随后读回全部属性，逐字段核对值。每档还保留写端实测固定步/秒、写入间隔 P95、被看到的版本轮次和写端各轮第一个字段在远端出现的时延 P95。该时延统计只含至少有一项抵达的轮次。空闲对照从基线就绪后连续采样 6 秒，计数结算后再逐字段读回。

## 结果解读

5,000 个属性每 100 ms 全改一次，业务提供约 50,000 次字段变化/秒。自研两次实测写端推进 17.4–17.6 个固定步/秒，远端在写入期间观察到 6,237–6,456 次变化/秒；停写后 418–857 ms 所有终值正确。Fusion 写端两次均约 60 步/秒，写入期间远端约 4,984 次变化/秒，停写后 1,736–2,481 ms 终值全部正确。测试值能放入 32 位；实际声明的 Godot `int` 是 64 位。自研按每字段 8 字节采集，Fusion 为每字段两个 32 位 word。按 50,000 次写入计，对应每秒 400,000 字节的未压缩状态值；实际线上字节量须另测。[采样与类型复核](property-profile.md)

同一批 5,000 字段按轮换的 10% 写入后，最终可见的中间版本比例从自研 14.2%–14.7% 提高到 89.8%，Fusion 从 15.0%–16.7% 提高到 98.3%。自研写端仍只有 18.6 步/秒。另一组 1,000 字段稀疏写入试验，两端产品的远端都看到了全部 6,000 次有效变化；从首次应用到结束，自研远端约调用 60,000 次 setter，Fusion 约 6,000 次。这与自研按对象完整回写的代码路径一致。稳定属性的读取则可独立用空闲组计数。

5,000 字段静置约 6 秒时，自研两端各调用 575,000 次 getter，均无 setter，约 19.2 步/秒；Fusion 写端调用 1,800,000 次、观察端 0 次，均无 setter，约 60 步/秒。在这一负载下，写端没有业务写入仍能重现自研端的步速下降。观察端扫描已确认有成本；扫描、对象调度和原生层分别占多少 CPU 时间仍需分项采样。

## 比较边界

把对象数一直固定在 250 个，只把每对象字段从 4 个加到 12 个、20 个，总属性为 1,000、3,000、5,000。自研写端约 60.5、28.3、17.6 步/秒，Fusion 写端约 60.0、59.8、60.0 步/秒。持权端下降的现象在对象数固定时仍能复现。首轮 20 字段布局和固定对象布局在 5,000 这一档相同，表中复用同一次测量。

另用该版原生 Godot 单独实例化探针脚本，不连接网络。给 20 个属性各赋一次新值，计到 20 个 getter 和 20 个 setter；再次赋相同值，仍计到 20/20。原因是探针 setter 会读取旧值来判重。因此有改写时，原始 getter 数包含判重读取；空闲数据的 setter 数在两条路径上均为零，适合用于比较框架自身的读取行为。

同一平台内改变属性数、对象数或每轮变更比例，可以观察它们怎样影响该运行路径。两套产品的运行时和网络路径不同，不能用这个对照给协议编码、带宽效率或同网条件下的产品性能排名。计数 getter/setter 的脚本也有成本。数据覆盖单写端、单观察端和短窗口，字段都是确定性变化的标量整数。多写端、不同兴趣区域、字符串或容器需要另设负载。

## 实现路径

在自研 Godot 插件中，每个复制节点的固定回调先调用 `sample_fields()`，遍历本节点的字段并按属性路径读取，然后才把完整采样交给 `sync_replica()`。Core 在观察端比较权威呈现值、上一版本以及本地采样值，能把业务对只读代理字段的本地改写纠正回来。需要回写时，普通属性布局遍历所有配置字段。网络快照编码另有按对端 ACK 生成的字段变化掩码。[Godot 采样和应用](../../../engineplatform/godot/replicated_object.gd#L166) · [Core 观察端判定](../../../core/session/script_game.cpp#L216) · [按字段写包](../../../core/state/replication.cpp#L572)

可单独验证两种改动的效果。第一种给只读代理提供按版本应用的路径，把本地写入纠正限制到实际被脚本修改的字段，同时保留现有纠正行为。第二种把收到的字段变化掩码传到 Godot 绑定层，只调用变化字段的 setter，初始基线和写权切换时完整应用。分别复跑 5,000 字段空闲、10% 变化和全量变化，观察远端 getter、setter、写端步速和停写收敛的变化。若空闲时改善而全量时仍慢，应再单独计时字段采集、序列化、发送排队和应用阶段。
