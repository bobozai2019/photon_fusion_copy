# Godot 属性复制的性能剖析与架构对照

本文的采样次数、字段格式和时序属于 2026-11-22 实测的 Godot 插件。源码链接用于定位兼容脚本和 Core 中对应的处理位置；现行原生节点的采集、逐 word 检测和代理应用见[运行时架构](../../../docs/architecture.md)。

实测于 2026-11-22。负载与前一轮一致：250 个普通 Node3D，每对象 20 个独立整数，一个玩家持有全部对象，一个玩家观察。固定 6 秒窗口分别测空闲、每 100 ms 轮换写 10%、每 100 ms 全写。自研使用 Windows x64 Release 插件、Godot 4.7.1 和本机回环，Fusion 使用 Preview 555 原版 Web 插件、随包模板、两个 Chrome 客户端和 Photon Cloud Asia。两端先核对基线，结束后读回所有终值。数据来自每种配置的独立房间。[上一轮 26 场属性实测](property-scale.md) · [本轮结构化 profile](property-profile.json) · [复现入口](../probes/property_profile.py)

## 复制路径

| 环节 | 自研 Godot 插件 | Fusion Preview 555 | 证据 |
|---|---|---|---|
| 场景和角色 | 复制节点登记属性清单，运行时按对象和写权代数决定哪个玩家可提交 | SharedReplicator 登记属性清单，实验对象由创建它的玩家持权 | 两端均由实际 Spawner 生成，按独立对象身份核对基线与终值 |
| 普通属性绑定 | 缓存根节点弱引用、规范路径和类型；通用采样逐字段取目标并用 indexed 属性接口读取 | 同构建 Linux 原生缓存项含目标节点、实例 ID、属性名、路径及 word 偏移。有效时直接按属性名读，失效后重建 | [自研通用采样](../../../engineplatform/godot/replicated_object.gd#L109) · [原版绑定、换节点实测](property-binding.md) |
| 整数表示 | `integer64` 映射为 Core 的 `bytes` 字段。每次通用读取创建 `Values` 编码器，把值放入 8 字节 PackedByteArray，GDExtension 再转换为 Core Values | 单个 Godot `int` 在对象布局增加两个 32 位 word | [类型映射](../../../engineplatform/godot/scene_fields.gd) · [编码](../../../engineplatform/godot/scene_values.gd#L15) · [GDExtension 边界](../../../engineplatform/godot/game.cpp#L911) · [原版类型布局](native-runtime.md) |
| 权威端变化检测与发包 | 比较当前字段集合和上一份 Values。Core 依据对象修订、各字段变更版本与各接收方 ACK 决定字段掩码，编码选中的整个字段值 | Linux 客户端有 Words 与 Shadow 的逐 word 比较、变更版本及 WriteDirtyWords。打包选取与 Shadow 更新是两个环节 | [自研状态判定](../../../core/session/script_game.cpp#L216) · [字段掩码](../../../core/state/replication.cpp#L572) · [原版 Shadow 和确认路径](property-binding.md) |
| 观察端读取与应用 | 每步先采本地属性再进 Core；网络掩码用于更新本地对象状态。向 Godot 返回完整字段集合时，适配层逐字段回写，可以纠正观察端的本地偏差 | 稳定代理未观察到 getter/setter；稀疏变化呈按变化字段应用的行为。观察端本地值被改动后，邻字段的更新仍保留这个偏差 | [自研接收解码](../../../core/state/replication.cpp#L711) · [Godot 回写](../../../engineplatform/godot/replicated_object.gd#L139) · 本轮本地写入实验 |

Linux 静态符号用于辨认算法和布局，Web 数据用于观察在线行为；只对 Web 插件本身导出的函数索引给出精确符号名。此次普通整数高 32 位恒为零。Fusion 按 word、自研按字段选择变化，两种粒度在这种输入上可能产生不同码流。实际每包字节、压缩比以及后端排队耗时仍不能从这些 profile 推出。

## 计时口径

自研在临时安装副本的复制回调中围住采集、`sync_replica`、应用，以及 Spawner 的 `room.advance`。采集含路径/类型处理、Godot getter 和字段编码；同步调用含 GDExtension 值转换和 Core 比对；应用含收到非空结果后的处理和写属性。三项按高精度墙钟计时，除以本端实测固定步数。复制回调总时间包含三项，不能再与三项相加。另用 Windows GetProcessTimes 计每个客户端进程的 CPU 秒。分页、线程调度和计时探针本身均可能影响墙钟读数。

Fusion 用 Chrome DevTools Protocol 对两个页面的主 isolate 分别启动 CPU 采样。从每个 Godot 客户端记录的 `performance.now()` 起止时刻，经同一页面的 NavigationStart 投到采样时间轴，仅统计六秒窗口内的样本。模块根据随包 Wasm 的长度、调试元数据识别，保留扩展栈及精确匹配的 Web 导出符号。包含扩展栈的样本可以正在 Godot 或浏览器内部执行，独占叶帧只看栈顶。两者均为样本个数。CDP ProcessTime 另按自身采集窗口求差，覆盖对应渲染进程。浏览器的 WebGL/JS、等待、编辑器插件静态指令和自研墙钟分段代表不同口径。[Chrome CPU 采样协议](https://chromedevtools.github.io/devtools-protocol/tot/Profiler/) · [采样裁切与归类](../probes/property_web_profile.py)

## 六秒采样结果

自研表中的毫秒均按本端实际完成的每个固定步归一化。进程 CPU 百分比按一个逻辑核心为 100% 计算，反映整个进程。

| 负载 | 角色 | 步/秒 | 采集 ms/步 | 同步调用 ms/步 | 应用 ms/步 | 房间推进 ms/步¹ | 进程 CPU |
|---|---|---|---|---|---|---|---|
| 静置 | 写端 | 18.0 | 47.28 | 4.32 | 0.00 | 0.04 | 100% |
| 静置 | 观察端 | 17.6 | 47.91 | 5.08 | 0.00 | 0.01 | 100% |
| 轮换 10% | 写端 | 18.5 | 44.65 | 3.83 | 0.00 | 1.06 | 100% |
| 轮换 10% | 观察端 | 16.5 | 45.55 | 5.04 | 5.99 | 0.27 | 100% |
| 全量变化 | 写端 | 17.4 | 44.49 | 3.49 | 0.00 | 1.53 | 100% |
| 全量变化 | 观察端 | 17.5 | 45.40 | 3.70 | 4.23 | 0.23 | 100% |

¹ 房间推进实际发生在渲染/处理回调。按固定步分摊，仅用于比较同一窗口的累计量。

Fusion 的栈计数使用六秒游戏窗口裁切后的 Chrome 主 isolate 样本。包含扩展是栈上出现过 Fusion 模块；独占扩展是栈顶在该模块。渲染进程 CPU 使用单独记录的 CDP 计数区间。

| 负载 | 角色 | 步/秒 | 总样本 | 包含扩展 | 独占扩展 | 渲染进程 CPU |
|---|---|---|---|---|---|---|
| 静置 | 写端 | 59.9 | 1960 | 437 | 85 | 36% |
| 静置 | 观察端 | 60.1 | 1970 | 19 | 9 | 11% |
| 轮换 10% | 写端 | 59.9 | 1964 | 436 | 93 | 42% |
| 轮换 10% | 观察端 | 60.1 | 2045 | 85 | 23 | 20% |
| 全量变化 | 写端 | 59.9 | 1778 | 401 | 91 | 53% |
| 全量变化 | 观察端 | 59.9 | 1789 | 93 | 14 | 22% |

写端确实采到了与 Web 原版导出表索引精确匹配的 `UpdateFrameEnd → PacketQueueState → WriteObjectRoot`。全量写入的观察端采样也命中 `StatePacketReceived`。多数高频的 Godot 绑定帧在 Web 发布物中没有导出函数名，保留函数编号。栈上也常见浏览器 `getParameter`，不能把这段运行时的耗时计给网络协议。

表中 Fusion 稀疏场次的六秒窗口有效。该场写端 5,000 个终值正确，观察端在结束通知后的 12 秒等待期末只有 3,500 个正确，字段身份与版本次序检查无错误。将调试器读取模块元数据移到终值校验之后再独立建房复测，远端在停写后 2,062 ms 收齐 5,000 个终值，累计看见 30,000 次变化中的 29,500 次。两次都保留在数据中。该组无法区分调试器扰动、云路径或其他运行时因素的贡献。

## 行为对照与实现边界

在空闲 profile 结束且双方均验证了 5,000 个终值后，观察端把字段 A 从 47,938,707 本地改为 0。两边均立即读回 0，权威端仍为原值。至少 750 ms 后，自研观察端已恢复 47,938,707，Fusion 观察端仍为 0。随后权威玩家只修改同一对象的字段 B；等 B 的新值 222,079,034 在观察端可见时，两端对 A 的读数仍分别为 47,938,707 和 0。最后权威端改 A，两边观察端均读到 365,247,635。这证明当前配置下的普通属性具有两种不同的本地纠偏行为。它不涉及写权转移或物理预测。

自研两项对照只改变临时副本的根节点整数读取，保留完整字段遍历、每个 getter、8 字节字段格式、网络协议、写权和原有回写路径。第一项缓存属性名、每对象每步只取一次根节点，按已知整数类型直接调用原有编码器。第二项在第一项上直接构造相同的 8 字节有符号整数，省去每字段创建的 RefCounted 编码器及其方法调用。它们用于区分绑定与整数转换的成本。通用实现还要处理子节点与资源路径失效、容器、基线、写权切换和本地偏差纠正。
