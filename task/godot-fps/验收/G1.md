# G1 房间与席位

2026-11-22，Windows 10 x64，Godot 4.7.1.stable.official.a13da4feb。插件 ZIP SHA-256 为 `5e189122ef8c7bbd863fffd18f86b5b4d8db2ad1f366839b8f2af8086bbb9941`。

```powershell
python -B tools/prepare_godot_fps.py
python -B tools/verify_godot_fps.py --suite rooms
```

| 用例 | 实测 |
| --- | --- |
| V1 正常入口 | 在编辑器中按 F5 进入大厅，点击 Host。实际选择的 WLAN IPv4 显示在计分顶栏，1/8，可单人进图。同机独立进程从按钮 Join，房主和客人都可移动。 |
| V1 错误恢复 | 非法地址、端口 0、占用端口、取消连接和不可达地址均返回可操作大厅，随后从同一菜单成功加入。连接超时会提示检查地址、端口和可用席位。 |
| V2 进退 | 客人主动退房和杀进程后，房主名单各回到 1 人。主动退房后重进获得新身份。房主主动退出或被关闭，客人回大厅并可重新开房。 |
| V7 满员 | 同机 1 主 7 客的 8 份名单身份一致，4 对 4。第九个进程无法获得席位。杀掉第八个进程后，原第九个进程取得新身份补位到 8/8，个人局数据为初始值。首次通过时房主延迟 0 ms，7 名客人各 17 ms。 |

复现脚本以 0 退出，Godot 日志错误数为 0。探针仅位于临时验收工程，从正常主场景启动，输入昵称、端口和地址后触发大厅按钮。

首次可视联调发现房主的昵称和队列可能恢复为初始值。最早分歧位于固定对象第一次 `sync_replica`，它会应用生成基线。如果只是输入框提交失败，槽位仍会留在原队。实测同时发生了阵营切换。房主现等待固定对象首次采样后再分配身份和写入资料，F5 开房和后续联机复验覆盖了该路径。

使用本机 WLAN 地址重复运行可视验证，满员时 7 位客人样本为 23–35 ms，房主为 0 ms。扩展的同机测试在满房完成补位后的移动、射击和补给，再主动腾出一个席位并重进。原房主关房后，7 位客人均返回大厅。[大厅](G1/lobby.png) · [满员人员表](G1/full-roster.png)
