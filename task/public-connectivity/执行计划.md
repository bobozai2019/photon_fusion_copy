# 公网连接执行计划

## 1. 目标

验证两个 Windows x64 Unity Player 通过可配置的 IPv4 端点运行现有车场，支持部署在可转发 TCP 和 UDP 入站流量的公网端点后。2026-11-20 确认以技术能力为交付目标，允许在本机验证。验收覆盖 TCP 建连、UDP 握手、属性同步、RPC、对象创建销毁和重连后的场景恢复。真实公网部署条件保留在执行状态。[第一阶段范围](../../docs/roadmap.md#第一阶段验收) · [现有 Unity 同引擎基线](../unity-platform/验收/验收.md)

## 2. 范围和运行模式

| 分类 | 交付范围 |
| --- | --- |
| MVP | Unity ↔ Unity 公网直连。房主有可入站的公网 IPv4，或其路由器可以把同一 TCP/UDP 端口转给房主 |
| placeholder | 公网中继接入点放在 `Transport` 下。只有直连入口不可获得、且必须保留家庭房主时再选中继方案 |
| vNext | Steam P2P 实机中继、房间码、公网域名与 IPv6、公开运营前的身份认证和加密 |
| out_of_scope | 跨引擎场景同步、房主迁移和模板/对象工厂重构 |

| 运行模式 | 环境 | 用途 |
| --- | --- | --- |
| 回环基线 | 同机两个 Unity Player，`127.0.0.1` | 复用已有证据。Player 或网络代码有变更时做回归 |
| 本机转发 | 同机两个同版 Unity Player，经独立监听地址转发同一 TCP/UDP 端口，并改写来源端口 | 本期技术验收 |
| 外网直连 | 两条独立网络，同版 Unity Player，同一公网 TCP/UDP 端口 | 实际部署时验证 |
| 公网中继候选 | 家庭房主无入站能力，两端可主动出站 | 届时比较现有 Steam P2P 和自建中继，形成独立实施决定 |

## 3. 需求映射

| 需求 | 任务 | 可观测验收 |
| --- | --- | --- |
| 可通过转发端点进房 | T01–T03 | 客人通过与房主监听地址不同的端点加入，双方有 TCP 和 UDP 流量，客人到达 `Ready` |
| RPC 和状态同步 | T04 | 开门请求在房主执行，客人收到结果。两端观察到属性变更、对象创建和销毁 |
| 断线接回当前场景 | T04 | 恢复同一 `PlayerId` 和 `ObjectId`，离线期间仍存活的对象补齐，已销毁对象未重新出现。双方最终状态摘要一致 |
| 可复查 | T05 | 记录同版构建指纹、拓扑、命令、双方日志、摘要和退出码 |

## 4. 保持的连接契约

| 交界 | 字段及语义 |
| --- | --- |
| 启动参数 | 房主 `--host --bind <本机网卡IPv4> --port P`。客人 `--join <公网IPv4> --port P`。项目当前解析 IPv4 字面量，控制和游戏使用同一个端口号 |
| TCP 控制 | 长度帧携带连接 cookie 和房间控制消息。双方保留已有 250 ms 心跳与 3 s 默认超时作为首轮基线 |
| UDP 配对 | 客人带 TCP 发放的 16 字节 cookie 探测。房主检查源 IPv4 与 TCP 对端一致，再记录 UDP 地址和端口。双通道就绪后才产生 `EventType::Open` |
| 游戏报文 | `GameMessage u8 + RoomId u64 + RoundId u64` 后接对应负载。`Lane::Game` 游戏负载上限 1,176 字节，房间和 RPC 仍通过现有 `Transport` 事件及收发接口 |
| 重连 | 新连接使用新的 `Peer`。客人提交 `RoomId u64 / RoundId u64 / PlayerId u32 / Key 128 位` 的现有恢复票据。房主验证后发送当前基线，客人满足 `Ready` 条件后恢复输入 |
| 失败观测 | 分别定位 TCP 无法建立、UDP 握手未完成、房间拒绝、基线未完成。只有现有日志无法区分时才补打阶段与断开原因，日志记录阶段、时间、构建和连接结果 |

## 5. 执行顺序

```text
T00 仓库与基线
  ├─ T01 核实网络入口与端口映射
  └─ T02 准备同版 Unity Player 和本地日志
T01 + T02 → T03 经转发进房 → T04 游戏同步和重连 → T05 验收归档
实际部署无入站路径 → 先评估可用公网房主 → 必须保留家庭房主时转中继方案
```

T01 的网络核实与 T02 的构建准备可以并行。本机转发复用 Player 的直连启动入口，分别监听房主地址与入口地址。两端的游戏剧本从房主开始等待连接后依次启动。

| 任务 | 小目标 | 完成证据 |
| --- | --- | --- |
| T00 核对基线 | 找到房主和客人启动入口、协议边界及同机验收 | 现有代码、操作说明和同机报告 |
| T01 核实网络 | 确认本机转发拓扑以及实际部署的 TCP/UDP 入站前提，记录已经查明的网络条件 | 可复核的拓扑和端口记录 |
| T02 准备 Player | 两端用同一份 Windows Player，核对构建版本、原生插件及模板配置，各自保留日志 | 构建指纹和启动命令 |
| T03 转发端点握手 | 从客人连接转发端点，核对房间 `Ready`、双通道流量和改写后的来源端口 | 双端连接日志及转发统计 |
| T04 业务与恢复 | 执行现有正常剧本，再执行游戏通道故障注入。核对 RPC、属性、对象生灭、恢复身份和最终摘要 | 双端玩法日志、指标和截图 |
| T05 归档 | 填验收表。记录可复现的部署与已测网络边界 | `验收/公网验收.md` |

如果 WAN 地址是私网或运营商共享段，先确认外层 NAT 是否可控。无法配置上游入站时，可先用已有公网 Windows 主机运行同一房主做验收。若产品要求家庭房主持有权威，再决定用 Steam P2P 或可承载两路消息的中继。中继验证覆盖 `Control` 的可靠有序投递和 `Game` 的应用层确认及重发。[共享地址段](https://www.rfc-editor.org/rfc/rfc6598.html) · [端口转发说明](https://www.asus.com/support/faq/1037906/) · [Steam 中继文档](https://partner.steamgames.com/doc/features/multiplayer/steamdatagramrelay)

## 6. 三道验收门槛

- Gate 1 · 转发端点可达。房主和入口监听不同 IPv4 的同一端口。客人通过入口完成 TCP 建连、UDP 握手和 `Ready`，房主面对不同的 TCP、UDP 来源端口。
- Gate 2 · 数据正确。正常和游戏通道故障注入各跑一轮。核对开门 RPC、`net_input_x` 的 `0.75` 与恢复后的 `-0.5`、路障生灭、相同玩家和原车、两端一致的场景摘要，以及双方退出码 0。
- Gate 3 · 可复现。执行命令、构建指纹、网络拓扑、两端日志、故障计数和恢复耗时齐全。记录恢复耗时所包含的剧本离线窗口。

执行进度见[执行状态](执行状态.md)。技术验收以两轮 Windows Player 本机转发实测为准。实际接入网络需在部署时验证。

## 7. 验收命令和证据

从仓库根目录运行本机转发验收。脚本复用正常玩法校验，固定让客人连接 `127.0.0.2:43263`，将 TCP 和 UDP 转到房主 `127.0.0.1:43263`。转发器以 `127.0.0.3` 和各自分配的端口连接房主。正常和故障两轮的日志、截图及统计分别归入 `out/runs/last-pass/normal/` 和 `out/runs/last-pass/fault/`。

```powershell
python -B tools/verify_public_yard.py
```

### 实际公网部署命令

将 [执行状态](执行状态.md) 中的 Unity Player 目录完整复制到两端，并核对所列 SHA-256。从各自的 Player 目录运行。端口以 `43263` 为例。房主在路由器后的电脑上时，`--bind` 使用这台电脑的局域网网卡 IPv4。对外映射 `43263/TCP` 与 `43263/UDP` 到房主的同一端口。如果房主直接持有公网地址，在该网卡监听并放行对应入站规则。[Windows 防火墙规则](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/rules)

同机预检复用构建目录里的 Player，避免从新的临时路径启动时再次触发防火墙通知。房主使用固定的 Player 路径，在首轮前由管理员核对该路径和当前网络配置文件下的阻止规则。处理冲突后，为该程序放行 `43263/TCP` 和 `43263/UDP`，已知客人来源地址时可限定到该地址。[Windows 防火墙规则优先级](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/rules)

```powershell
# 房主窗口
$role = 'host'
$connection = @('--host', '--bind', '<房主本机IPv4>')

# 客人窗口，在另一条接入网络上运行
$role = 'guest'
$connection = @('--join', '<房主公网IPv4>')
```

每端先设置自己角色的两行，将尖括号内的地址替换为本次测试的实际值，再执行下面的采集命令。房主的输出出现 `listening port=43263` 后立即启动客人。`play` 剧本默认自进程启动计时，40 秒后截止。正常轮结束后，两端将 `$run` 改为 `'fault'` 并复跑。

```powershell
$run = 'normal'
$stem = "$run-$role"
$playerArgs = @('-logFile', '-', '-screen-fullscreen', '0', '-force-d3d11', '--') +
    $connection + @('--port', '43263', '--scenario', 'play', '--trace', '--capture', "$stem.png")
if ($run -eq 'fault') { $playerArgs += '--fault' }
$player = Start-Process -FilePath '.\netcode-unity.exe' -ArgumentList $playerArgs `
    -WorkingDirectory (Get-Location).Path -RedirectStandardOutput "$stem.stdout.log" `
    -RedirectStandardError "$stem.stderr.log" -Wait -PassThru -ErrorAction Stop
if ($null -eq $player.ExitCode) { throw 'Unable to read the Unity Player exit code.' }
$player.ExitCode | Set-Content "$stem.exit.txt"
```

`tools/verify_yard.py` 启动本机的两个进程，默认用回环地址。可用 `--local-address <本机IPv4>` 检查本机网卡绑定和双通道消息。外网用例使用上面的分机命令。

证据记录使用房主和客人的 `summary`、`door_open`、`peer_lost`、`recovered` 与对象生灭日志。正常轮和故障轮分别记录网络类型、端口、构建指纹、双端状态摘要、TCP/UDP 字节数及恢复耗时。截图用于核对两端真实运行窗体和当前场景。
