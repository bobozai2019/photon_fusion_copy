# T6 · 空间兴趣与服务器输入

两进程使用 Godot 4.6.1 Windows x64 和 TCP 回环。独立断言验证空间场景和输入模型。

| 能力 | 断言 |
| --- | --- |
| 空间网格 | 客端观察者从 x=2 移到 x=26。近处节点释放，远处节点出现并读到 802。Host 在观察者离开期间把近处字段改成 803，观察者回到 x=2 后读到 803。 |
| 输入队列 | Host 给玩家 2 输入权威。B 连续递交编号 1 至 12，立即预测得到 12，队列含 12 条。A 按原顺序执行，每条一次，得到 24。 |
| 校正与重演 | B 收到权威帧后重演未确认的输入，最后确认到 12，队列清空并得到 24。重演次数随分帧变化，最后的确认号与状态固定。 |

首版构建 `f02e836d260f61d4/a8cc6147f47b909c` 的 Godot 4.6.1 运行记录了 66 次重演，Godot 4.7.1 Windows Release 导出记录了 78 次。两组均确认至 12，实际消费的输入序列均为 1 至 12，四个进程退出 0。

使用 `python -B tools/verify_godot_native.py --addon <SDK ZIP> --case simulation` 复跑。模型故意让房主与预测器每次加不同的值以触发校正。

第一轮追加默认 60 Hz 下连续 360 个物理帧的输入。房主和客端均确认至 372，最终字段为 744，客端稳态测试区间的队列峰值为 4。

第二轮将授权移到房主的 `pre_spawn`，校验入树前暂存及实例上树后绑定。房主和客端的非中立输入回调均断言步长 16 ms，包含客端重演。数据继续收敛至确认序号 372 和字段 744。

新版在 Godot 4.6.1 的客端稳态队列峰值为 3。Godot 4.7.1 Windows Release 导出双端复跑也确认至 372、字段 744，客端峰值为 3。客端在自己已订阅的 x=2 格子提交空间生成，随后收到正式写权基线。

v3 将输入权从已清空队列的客端切到房主。客端提交输入返回 `false`。房主将另一个浮点字段从 0 改成 100，客端先显示中间值，再精确命中 100，随后六个物理帧内 setter 的调用数保持不变。房主在预分配输入权的情况下收到一次状态写权通知。用例未覆盖有在途输入时的切权。

v4 用 `queue_input(delta, payload)` 提交 12 条不同步长的输入，对每次初次预测、权威执行及重演核对逐条 delta。零、非有限、超出 float32 范围及窄化到零的 delta 均遭拒绝。再以单参数模式按 60 Hz 提交 360 条，房主和客端确认到 372，最终字段均为 744。此次客端队列峰值为 3。用例验证回调收到的 delta，房主仍按 16 ms 服务步消费指令。

## v5 输入消费

Core 手动时钟单测按顺序提交 48、8、8 ms 三条输入。房主前两次 16 ms 服务步均等待，第三步执行 48 ms，第四步依序执行两条 8 ms。每条都有独立模型 tick。房主在服务时钟未推进时提交本机输入，立即执行并确认。跨五步追赶时不重跑已覆盖的时间；迁移后继续抵扣 32 个服务步，并保留模型 tick 的顺序。换权清空旧队列及累积时间。旧式 Core 模型保留固定消费。

Godot 双端验证房主本机调用返回前已提交，累计确认至 372，最后字段为 744。中途由输入回调移除 Spawner 时，房主延后执行清理，客端旧节点也被回收。Fusion 555 的静态证据支持队首计时与 Master 直接分派，既有双端轨迹使用相同 delta。Netcode 由房间处理器驱动，Fusion 暴露 `process_input_queue(delta)`，以及发生在重演前的 `state_reset`；这两个玩法入口仍有差异。[555 输入证据](../../../research/fusion/findings/native-runtime.md#client-server-的输入发送消费和重演)
