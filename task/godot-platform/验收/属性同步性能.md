## 实现取舍

Godot 适配器在绑定时保存成员名及路径。只包含根节点整数的布局在读回时重用各字段的上次编码。缓存的八字节值由实际 getter 结果驱动，子节点和嵌套资源则沿当前路径解析。同路径替换用例区分了缓存访问路径和缓存目标实例的行为。先保留旧节点存活，再测试旧节点释放，两次均由新节点获得权威值。

脚本会话继续返回完整呈现值。适配器根据本步实际读到的值选择稳定期的 setter，保留基线全写及本地误写纠偏。代理误写时网络通常没有产生变化。只按收到的包掩码回写会延迟该字段恢复，750 ms 静置检查可以区分两种实现。引用解析和已启动的插值仍由本地固定步推进。

## 2026-11-23 八人限带宽与构包准入

**主张和实现。** Fusion 的 `PacketQueueState` 先查 `Notify::Connection::CanQueue`，通道有容量才构建状态包。本机 TCP 采用可靠有序 FIFO。若某一连接已明确得到底层 `Blocked`，房主先等 TCP 模块接收 Core 暂存的未提交队尾，再按该连接的 ACK 和当前对象版本构包。每次跳过只针对这一连接的状态构包和压缩。写权、RPC 和控制消息可以继续入队，其他连接独立发送，AOI 切换后的完整基线由对象版本记录生成。[Fusion 指令核对](../../../research/fusion/findings/property-binding.md#八人场剩余的房间推进开销) · [构包入口](../../../core/session/game_session.cpp) · [队列准入](../../../core/session/outbound.cpp)

**验证与边界。** 八端、512 对象、60 轮写入。只在写入期间限制客人 B 的 TCP 下行，目标 8 KiB/s，压测连接的接收缓冲 4 KiB，TCP 模块队列 65,538 字节。保留第 30 轮 AOI 切换，其他六名客人必须在解除限速前完成切换，解除后等待 B 切换，再令八端恢复全可见并逐字段对齐。`snapshot_backpressure_skips` 统计房主写入窗口内因 FIFO 阻塞而跳过的连接发送步数。机制覆盖传输模块已显式反馈的阻塞。TCP 内核和模块已接收的数据继续按序交付。[复现命令](../../../research/fusion/probes/README.md#纯属性数量与变更比例)

### 客机上行持续写入的积压复测

第二轮代码审核基于 SDK `57b743d`、示例 `0bda59c`、插件 `b8ddb4c42aa28592/64ddb8f2e3eed214`，环境为 Windows x64 和 Godot 4.6.1 同机双进程。C 档 1024 怪定向夹具关闭自动攻击，由房主和客机继续推进各自持权怪物。relay 附加 40 ms RTT，连接后的第 6 至 12 秒仅限制客机到房主方向，设置为 8 KiB/s，限速窗口实际转发 44,032 B。夹具放置 240 颗经验石，并丢弃客机收到的第一份升级结果。

| 指标 | 实测 |
| --- | ---: |
| 客机 TCP provider 与 Core 待发合计采样峰值 | 783,084 B |
| 客机业务 RPC 待发加在途峰值 | 14 条 |
| 客机最老业务消息队龄峰值 | 5908 ms |
| 从放置经验石到客机全部收齐 | 约 5.2 秒 |
| 升级发起到确认，含一次重试 | 1134 ms |
| 恢复后双端结算 | 240 次拾取、240 XP、1 次升级 |

`ObjectAuthority::flush` 只对同一修订的补发应用 200 ms 间隔。持续变化的新修订仍可逐步编码并进入客机上行队列。业务优先级作用于提交前，已经排在同一 TCP 流中的状态字节仍按序发送。这里的 200 ms 边界由代码确认，队列峰值和时延来自上行限速实测。Core 9/9 与独立 Core 消费者测试均通过。此前单包公平性、同一修订重发和下行限速结果仍适用。

**待处理。** 为客机持续写入增加逐连接提交预算，在编码前保留同一对象的最新待发修订。限速链路本身也会推高确认时延。可用相同限速窗口对照启停持续写入，再比较引入上行预算后的待发峰值、首条和全部拾取确认时延以及写入终值。记录恢复期间的收敛时间和链路字节量。[客机写入发送路径](../../../core/session/object_authority.cpp)
