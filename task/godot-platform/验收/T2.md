# T2 · TCP 直连、单例与房间属性

Godot 4.6.1 Windows x64，原生 `Netcode` 的 TCP provider 在 IPv4 回环上监听。房主、首位客端和晚加入客端为三个真实进程。两个生成器登记到同一会话，场景树只出现一个插件创建的推进节点。

| 用例 | 断言 |
| --- | --- |
| 无效地址和端口 | 请求立即返回 `ERR_INVALID_PARAMETER`。 |
| 端口正在监听 | 另一进程返回 `ERR_CANT_CREATE`，房间视图为空。 |
| 空闲端口 | 加入请求开始后收到 `connection_failed`，没有入房信号。 |
| 入房和属性合并 | 房主首值为 `lab-size=128`、`lab-progress=0`。B 提交 `lab-progress=76` 和 `lab-area=1`。A 读到后提交 `lab-ready=true`，B 和晚加入者读到最新基线。 |
| 离房再监听 | 原房间视图失效，当前进程用原端口重开，再次收到入房与离房信号。 |

复跑时执行 `python -B tools/verify_godot_native.py --addon <SDK ZIP>`，记录 `nodes`、`unreachable`、`occupied`、`host`、`guest`、`late` 的断言与构建 ID。

## 原生协议 v3 复审

Godot 4.6.1 验证了房主与客端的 `get_players()`、房主身份和玩家进出信号。三进程夹具暂停观察者的会话推进，第三位玩家入房，在房主的 `player_joined` 回调收到定向房间 RPC 后离房。观察者恢复时，加入与离开回调依次读取到三人和两人名单。初版 v3 候选在同一用例中漏掉了两条信号。

客端用同一预期值先后提交两批条件更新，房主只提交第一批。删除的键在房主、客端和晚加入端均消失。房主还验证了字典键顺序、空值与删除的区别，以及对象嵌套、对象型容器和不可无损解码数据的拒绝。

原生 v2 和 v3 分别作为房主和客端运行。两个方向都在协商阶段拒绝，客端没有进入房间。非原生房主也没有让 v3 客端误判入房。复跑使用 `python -B tools/verify_godot_native.py --addon <v3 SDK> --legacy-sdk <v2 SDK>`，单独验证玩家名单用 `--case roster`。
