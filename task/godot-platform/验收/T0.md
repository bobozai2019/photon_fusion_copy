## 双端记录

Photon Cloud Asia，A 建房为玩家 1，B 加房为玩家 2。场景将 Owner Mode 设为 Player Attached。两端退出码均为 0。两端在 `room_joined` 时的网络时钟为 0，之后各自观测到正值。下表按各进程事件顺序记录，进程启动时刻各异。

| 端 | 事件序列 |
| --- | --- |
| B，生成端 | 入房 → 时钟可用 → 调用 spawn → 回调收到 `(FusionSharedReplicator, Node2D)` → 回调读到 `-1`、有权威 → setter 写 `731` → `_enter_tree` 读到 `731` → `_ready` 读到 `731` → Replicator spawned → Spawner spawned → 同步返回节点、读到 `731` → `authority_changed(true)` |
| A，观察端 | 入房 → 时钟可用 → `_enter_tree` 读到 `-1` → `_ready` 读到 `-1` → 首次 setter 收到 `731` → Replicator spawned 读到 `731` → Spawner spawned 读到 `731`。全程无本地权威。 |

B 调用、返回和生成信号均在网络时钟 5.661 s 的同一帧。B 的权威通知在 5.944 s，A 的首次 setter 在 A 时钟 6.326 s。两个网络时钟的差值保留作诊断，未用来估算单程延迟。

## 边界与实现影响

**主张。** 回调在生成端入树前以两个参数调用，观察端在 `_ready` 后、生成信号前收到首份字段。**依据。** 上述两进程序列和字段值。单参数回调的一轮没有触发预写，A 的首值是 `-1`。**边界。** 本实验覆盖 Cloud Asia、Player Attached 及整数直接复制。Local 模式的房主先返回 `Connection error: 1039 (code: -1)`，退出 2，未启动客端。本机当时没有 5055 的 TCP 或 UDP 监听者。**实现影响。** Netcode 的预回调采用 `(replicator, node)`，将其采样纳入生成请求，远端在 `_ready` 返回后安装基线，再发生成信号。

另一种实现可以让创建者先获得局部写权，再通过常规快照提交初值。抓取受控延迟下远端第一份赋值可区分两种行为。本计划将首值放进同一生成事务，原版的具体线格式仍未确定。

从 `netcode/` 运行 `python -B research/fusion/probes/spawn_order.py cloud`。Local 联机改用 `local`，手工默认值复查用 `defaults`。运行器读取本机 sync-lab 的设置，日志不包含 App ID。

## 同一调用栈中的返回后赋值

使用同一 Preview 555 的原版 Web 扩展和 Godot 模板，在 Cloud Asia 用 Player Attached 模板复跑。B 入房后分别在有、无预回调时生成。预回调写 `0.25`，两次都在 `spawn()` 返回后立即写 `0.75`。无预回调时 B 的 `_ready`、两个生成信号和调用返回读到 `0.0`。有预回调时四处都读到 `0.25`。两次 A 的 `_ready` 均读到 `0.0`，首个 setter 及两个生成信号都读到 `0.75`。旧解释“发出调用时立即冻结字段，再用下一条更新覆盖”会让 A 的生成信号看到 `0.0` 或 `0.25`，与这两次观测不同。

本轮 Windows 原版在 Asia 和 EU 都在入房前返回 `1040`，未产生 Windows 首值轨迹。Web 的已入房生成覆盖同一调用栈的写入，访问仿真时钟前的原版行为沿用上文的边界。从 `netcode/` 设置已有测试项目的 `FUSION_PROBE_APP_ID` 后运行 `python -B research/fusion/probes/cloud_web.py --mode spawn`。[官方生成用法](https://doc.photonengine.com/fusion-godot/v3-shared-authority/manual/spawning)
