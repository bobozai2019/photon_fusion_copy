2026-11-20，Windows 10 x64。同机测试使用 Godot 4.7.1 `a13da4feb`、NVIDIA GTX 1050、OpenGL Compatibility 3.3、MSVC 19.51。GDExtension 使用 godot-cpp `godot-4.5-stable`（`e83fd0904c13356ed1d4c3d09f8bb9132bdc6b77`），归档 SHA-256 为 `0316ea168750b5f4f1caea6457657a6c64241f890f78e2f042aee4be2b1085bf`。

## M6 四人百对象与交叉开房

Godot 房主、Godot 客人和两个轻量客人建立三条真实连接。四端分别取得 100 个对象，收敛的状态摘要覆盖对象 ID、模板、所属和每个编码字段。无故障场景的四端摘要为 `17926343862262366077`，故障场景的四端摘要为 `5558004399048449319`。场景以冻结后的同场四端一致性为验收。

两次观测均为 10.016 s。基线推进 300 个模拟步和 200 个发送步，3647 / 30000 个对象样本改变。故障场景推进 301 个模拟步和 200 个发送步，3676 / 30100 改变。四端共记录 150 次丢弃、207 次重复和 186 次乱序。两次均完成开门和可靠房间广播。

## Windows 导出和包内复跑

首次在空临时项目导入时，编辑器完成扫描后以 `0xC0000005` 退出。构建工具在编辑器初次扫描前登记该项目的 GDExtension，随后新建暂存项目的导入和 Windows 导出均退出 0。

发布包在 `out/packages/godot-win-x64/current/netcode-godot-win-x64.zip`，38615859 字节。SHA-256 为 `5dcf0e7d830f1a76f7e53aa5ef02a3cb6b9ea00f5a9be9a124835a2881c595d1`。包内含 Windows x64 Godot 可执行程序及内嵌资源、GDExtension DLL、轻量客人、共享配置与上游许可。解压后空窗、绑定和双窗完整流程通过。客人恢复原车耗时 1199 ms，两端均为 5 个对象，摘要为 `10471135894391265384`。

首次重复导出发现 Godot 为无 ID 的根节点分配随机 ID。场景声明固定 ID 后，重打包得到相同 SHA-256，工具报告 `unchanged`。轮换成功和发布失败回滚继续使用已实测的共用包槽逻辑。

```powershell

python -B tools/package_godot.py
python -B tests/integration/test_artifacts.py
```

## 场景生成与驾驶业务层

Windows x64、Godot 4.7.1，运行 `python -B tools/verify_godot_racing.py`。探针在两个独立进程中操作默认场景的创建和加入按钮，房主开标准车，后加入的玩家开跑车。检查两端各出现两辆车、本地实例获得写权、两侧各自观察到对方移动和倒车灯，客人离房后房主仅保留自己的车。预期输出为 `racing_pass host remote_removed=1` 和 `racing_pass guest own_write=1 remote_motion=1`。本机结果符合预期。位置断言包含显示插值的收敛容差。

对照依据为本地 Fusion Racing 3.0.0 场景中的生成器、玩家附属复制器与车辆输入脚本。该样例在入房回调内生成选中的场景。我们的玩家创建先由房主确认，返回实例前等待复制基线与写权。双端分别检查本地写权并观察另一端的动作，可区分真正的玩家写入和房主独自运行两辆车。本次实测范围为同机 Godot 直连。
