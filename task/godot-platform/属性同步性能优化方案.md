# Godot 属性同步优化方案 · 对标 Fusion Shared Authority

2026-11-22。目标是在 Godot ↔ Godot 的真实双客户端房间里同步 1,000～5,000 个普通属性，写端和观察端分别达到 Fusion 3 Preview 555 实测固定步速的 **至少 80%**，同时把远端实际看到的变化、终值正确性和停写收敛纳入验收。游戏继续在编辑器选择节点和属性，在脚本里正常赋值。

**进度**　SDK 优化和安装包验收 [已完成]。15 格全部达标，225 场基线和终值完全正确，固定对象数补充对照 18/18 场通过。相对 Fusion 最低的步速中位数比值为 94.1%。本轮结果见[性能验收](验收/属性同步性能.md)。下表为此前 26 场规模实验与 11 场 profile／对照实验，其中快路径来自临时副本。[规模实测](../../research/fusion/findings/property-scale.md) · [分端 profile 与失败场次](../../research/fusion/findings/property-profile.md)

八人混合诊断另取 Fusion 555 同负载参考。512 对象自研原问题布局完成原生采集优化和四房复验，模拟单程 40 ms 与抖动时房主达 49.6～51.4 步/秒。共同类型布局下自研房主约 60 步/秒，Fusion 主写端为 51.0。两组使用各自的运行时和链路，证据用于定位瓶颈。[八人实测](验收/属性同步性能.md#2026-11-23-八人场景与-fusion-对照)

## 从哪一处开始

| 5,000 个 Godot 整数，250 个对象 | 优化前发行版，写端 / 观察端 | 临时缩短根属性访问和整数编码后 | 原版 Fusion，写端 / 观察端 |
|---|---:|---:|---:|
| 静置 | 18.0 / 17.6 步/秒 | 60.0 / 61.4 | 59.9 / 60.1 |
| 每 100 ms 轮换改 10% | 18.5 / 16.5 | 60.1 / 44.9 | 59.9 / 60.1 |
| 每 100 ms 全改 | 17.4 / 17.5 | 尚待同负载验证 | 59.9 / 59.9 |

即使完全没有变化，发行版写端每步仍花 **47.28 ms** 采集，观察端花 **47.91 ms**。缓存根字段名并缩短类型分派后，两端降至约 19 ms，直接编码相同的八字节整数后又降至约 4.5 ms。两端仍逐步读取全部字段。因此先让一次属性访问足够便宜，再减少观察端的访问次数。稀疏组观察端 44.9 步/秒约为原版的 **74.7%**，完整回写还占 **7.33 ms/步**。[分项计时与受控实验](../../research/fusion/findings/property-profile.md) · [原始数据](../../research/fusion/findings/property-profile.json)

## 80% 怎么验

1. **固定输入。** 每对象 20 字段，依次测 1,000、2,000、3,000、4,000、5,000。每档分别静置 6 秒、每 100 ms 轮换写 10% 或每 100 ms 全写，活动组共 60 轮，合计 15 格。固定 60 Hz 目标、所有对象可见、无物理、相同值序列和终值校验。另用 250 对象 × 4、12、20 字段区分逐对象和逐字段开销。记录实际写入轮数、总数、持续时间和写入间隔 P95。减少输入、降低配置频率或过滤对象的场次均须重测。
2. **固定计分方法。** 同机、相同电源和后台负载，每格每版本至少五个独立房间，串行运行并轮换产品顺序。锁定旧发行版、候选版和 Fusion 的构建指纹。预热到两端基线就绪。用关闭 CPU profiler 的数据计分，另开同负载房间定位热点。补齐探针，在共同写入窗口记录两端各自的实际固定步数、墙钟和逐步间隔，避免把收包首尾之间的步数当作整个窗口的步数。每格、每角色取跨房间中位数，公布单场值与最差场。
3. **逐格判定。** 下表同时生效。空闲组的变化吞吐、版本覆盖和停写收敛记为不适用。每场都核对正确性。自研终值超时即该格失败。参考端单列成功率，公布所有尝试；有效完成场不足五场时该格记为待补证。

| 指标 | 发布门槛 | 用意 |
|---|---|---|
| 实际固定步/秒 | 两端各自 ≥ 48，且 ≥ 同格同角色 Fusion 中位数的 80%。计分时双方都以配置上限 60 截断，报告保留原值。 | 5,000 稀疏组须先把观察端从 44.9 提高到至少 48。并列每秒步数与步间隔 P95，用于识别卡住后集中追步。 |
| 停写前远端可见的不同字段版本/秒、累计版本可见率 | 两项分别 ≥ 同格 Fusion 的 80%。同机同路径的两项中位数还须 ≥ 自研旧版复测的 95%。 | 5,000 全改组 Fusion 旧读数约 4,984 次/秒，80% 约为 3,987。自研旧版已有约 6,237～6,456 次/秒。实际取两条门槛中的较高值。 |
| 停写至远端全部终值正确的时间 | 中位数 ≤ 同格 Fusion 的 1.25 倍，也 ≤ 自研旧版同路径中位数的 1.10 倍。每场沿用结束通知后 12 秒等待上限，另报最差值。 | 耗时越小越好，用 Fusion 耗时除以自研耗时计算相对表现。与可见率一起看，可查出停写后才集中补齐的情况。 |
| 正确性 | 每场基线和终值逐字段 100% 正确，身份和版本顺序错误数为 0。稳定等值时无业务 setter 回写。 | 状态复制允许合并中间版本。终值、写权交接、重绑、漏包合并与代理本地误写均单独核对。 |

**对标环境。** 自研是 Godot 4.7.1 Windows Release 无窗口双进程走回环，Fusion 是原版 Web 模板双 Chrome 客户端走 Photon Cloud Asia。主表衡量这两条路径的步速和最终交付。协议带宽效率或每字段 CPU 成本需另做同运行时、同链路的对照。在线条件难以对齐时，可先在同一原生运行时回放相同的属性访问负载，仅报告实际覆盖的层次。缺少可比数据的指标保持待测。浏览器采样数和原生分段墙钟分别解读。[计时口径](../../research/fusion/findings/property-profile.md)

## 实施顺序与判断依据

| 阶段 / 当前状态 | 参考 Fusion 的思路 | 在项目里的落点与阶段验收 |
|---|---|---|
| 0　冻结基准 [已完成] | 分开观测权威采集、网络投递和代理应用。 | 双端共用写端起止时间，独立统计步数、应用版本和终值。已核对锁定的发行 ZIP 和原版构建，少一轮自测已拒收。旧版和原版每格各五个有效房间。 |
| 1　注册时绑定属性 [已实现] | 原版普通字段保存目标实例身份、成员名、路径和布局位置。稳定目标直接读成员，目标失效后重绑。 | Godot 绑定缓存成员名与访问路径。同路径替换使用当前子节点，嵌套资源沿通用路径解析。子节点保留存活、释放及资源替换均通过双端回归。[原版缓存和替换实验](../../research/fusion/findings/property-binding.md) · [绑定入口](../../engineplatform/godot/replicated_object.gd) |
| 2　缩短持权端采集 [已实现] | 原版在固定布局上比较当前值和上次采样的影子值。一个 Godot 整数占两个 32 位 word。 | 纯根整数布局按模板顺序读成员，原值变化时更新八字节缓存。负数、两个有符号极值和只变高 32 位均通过回归。[类型转换](../../engineplatform/godot/scene_values.gd) · [原生同步入口](../../engineplatform/godot/game.cpp) |
| 3　观察端按变化字段应用 [已实现] | 原版稳定代理无字段读写，稀疏组的 setter 次数与可见变化相近。代理本地改 A 后，权威只改同对象的 B，原版仍保留 A 的本地改值。 | 候选版基线按序全写，稳定期依照当前场景值和完整呈现值挑选字段。5,000 稀疏首场双端约 60，setter 放大率 1.00。误写 A、静置、改 B、再改 A 的回归通过。[行为实测](../../research/fusion/findings/property-profile.md) · [脚本会话](../../core/session/script_game.cpp) · [适配层回写](../../engineplatform/godot/replicated_object.gd) |
| 4　定位全改负载剩余耗时 [已完成] | Fusion Shadow 记录已采变化，选择待发送状态另有确认路径。采样进度和各接收方交付进度可以独立观察。 | 5,000 全改的候选写端／观察端中位数为 59.9／56.3 步/秒。独立 profile 观察端采集、原生同步、筛选回写分别为 4.22／4.60／5.45 ms/步。全改各格达标。[现有复制实现](../../core/state/replication.cpp) |
| 5　用安装包验收 [已完成] | 用两个真实角色、相同输入和独立终值读回检验行为。 | 候选 ZIP 通过主矩阵、固定对象数对照、双进程属性契约、三进程晚加入和 9 项 Core Release 测试。验收 ZIP 已进入本地发布槽。[当前包与验收结果](验收/属性同步性能.md) |

阶段 0 完成后，绑定缓存与观察端正确性夹具可以独立准备。阶段 1、2、3 各自保留可复测的构建，在同一台机器串行压测以区分收益。前三阶段已达门槛时，阶段 4 只需记录全改分项并确认余量。

阶段 3 另设一个容易定位回归的检查。在 1,000 字段、轮换 10%、无插值、无本地误写的对照中，剔除初始基线和结束读回后，以观察端实际应用的不同字段版本为分母，普通属性 setter 调用数除以该数应 ≤ 1.10。若完整收到 6,000 次变化，最多执行 6,600 次。未收到的中间版本另由主矩阵的覆盖率约束。阶段 0 同时要更新临时计时插桩，现有原生 profile 探针按源码片段匹配，重构入口后必须核实计时仍覆盖同一个阶段。[现有插桩](../../research/fusion/probes/property_profile.py)

## 实现时要守住的三个约定

**绑定身份。** 模板保存字段身份、顺序、访问方式和编码类型，每个实例单独保存目标身份及有效期。Fusion 在一项实验中继续读已出树但尚未释放的旧节点。自研当前逐次从根沿路径查找，优化后应保持原有路径含义，专门测试旧节点仍存活和已经释放两种情况。未能可靠检测资源替换的嵌套字段，先沿用通用路径。[原版同路径替换过程](../../research/fusion/findings/property-binding.md) · [自研属性契约](../../docs/specs/property-binding.md)

**从 Core 到 Godot 的应用数据。** 建议内部结果携带对象身份、回合、写权代数、呈现版本、完整基线标志，以及按模板序号排列的变化字段和值。网络包掩码相对于发送方已知的确认点，脚本侧要覆盖自上次成功应用以来的全部变化。同一步先后收到两个包、重复包、字段先改后恢复、预测写权被拒、对象显隐及晚加入都要测试。完整基线先于新写端首笔提交。目标暂缺时保留待应用状态或在重绑时重放基线。引用的延迟解析和活跃插值要能在没有新包时继续推进。[接收与确认](../../core/state/replication.cpp) · [写权与呈现入口](../../core/session/script_game.cpp)

**业务脚本和代理本地写入。** 现有场景默认继续自动纠正只读代理的本地改写。对插件无法可靠截获的普通赋值和容器内部修改，兼容路径使用优化过的读回；能可靠订阅修改时才依赖通知。如果提供 Fusion 式“收到权威字段更新时覆盖”的策略，由场景显式选择并单独公布性能。**默认配置须过 80% 发布门槛。** 功能用例按顺序执行“代理误写 A → 静置 750 ms → 权威只改同对象的 B → 权威再改 A”，逐次核对 A、B 及权威原值。另用带副作用的 setter 核对基线、稀疏回写次数和顺序；旧场景确实依赖整对象重复回写时提供兼容路径。[官方属性复制说明](https://doc.photonengine.com/fusion-godot/v3-shared-authority/manual/replication/syncing-properties) · [本地误写实验](../../research/fusion/findings/property-profile.md)

## 遇到问题时怎么选下一步

| 症状 | 先做什么实验 | 根据结果怎么改 |
|---|---|---|
| 静置仍慢，网络几乎没有新数据 | 同一负载对照普通访问、缓存访问、八字节直接编码，分别看采集耗时和分配量。固定对象数改变字段数，再固定字段总数改变对象数。 | 耗时随字段数增长就收紧属性访问与编码；随对象数增长就检查逐对象调度、路由查询和跨脚本边界的次数。 |
| 写端已到 60，观察端稀疏负载过不了 48 | 分开数有效变化、setter、本地纠偏读回和活跃插值。1,000 字段稀疏组中，Fusion 约调用 6,000 次 setter，自研旧版约 60,000 次。 | 优先消除同对象其他字段的重复设置。若 setter 次数已接近有效变化仍慢，再量完整数组分配、复制和纠偏扫描，决定是否批量应用。 |
| 步速回升，终值丢失或交接后读到旧值 | 跟踪一个对象从采集、各接收方待发版本与 ACK、接收合并，到最终应用的回合、写权代数和版本。注入丢包、乱序、同一步多包、交接后的旧包。 | 从第一次出现差异的阶段修复。按接收方保留重发资格，按本地消费者保留待应用字段，两层分别清理。 |
| 全改时步速合格，但停写后积压 | 记录提交量、排队字节、最老待发版本、收包和应用时间。用同一链路重放相同数据，再分别只变整数的低或高半部。 | 编码或链路成为瓶颈才试更细粒度的变化编码；收包及时而应用延迟则优化解码和场景回写。单列云链路波动和失败房间。 |
| 两端都显示 60，仍能看见卡顿 | 检查逐步间隔 P95 和按秒分桶的最低步数，再看相同原生运行时的 CPU 秒、分配量、每个有效应用字段的代价。 | 有追步或长帧就按最慢窗口定位。60 Hz 封顶后的处理余量，以这些额外读数说明。 |

## 复现与交付

从 SDK 仓根目录启动，Fusion 探针沿用环境变量 `FUSION_PROBE_APP_ID`。以下命令可单独复测规模和 profile。正式五房发布验收使用 `property_matrix.py` 与 `property_verdict.py`。[完整矩阵命令](../../research/fusion/probes/README.md#纯属性数量与变更比例)

```powershell
foreach ($backend in 'native', 'fusion') {
    foreach ($workload in 'idle', 'sparse', 'dense') {
        python -B research/fusion/probes/property_scale.py $backend 1000 2000 3000 4000 5000 --workload $workload
    }
}
python -B research/fusion/probes/property_profile.py native --workload sparse
python -B research/fusion/probes/property_profile.py fusion --workload sparse
```

执行状态记入[同目录执行文档](执行状态.md)。安装包指纹、逐格判定和逐场读数见[性能验收](验收/属性同步性能.md)。原始输出按仓库规则轮换。[探针说明](../../research/fusion/probes/README.md) · [SDK 安装验证](../../docs/sdk-validation.md)
