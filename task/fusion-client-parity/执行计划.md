# Fusion 客户端能力补齐计划

本阶段的 `verify_plates.py` 混合引擎实验用于诊断公共 Core。产品验收按引擎分别组房，复跑同引擎玩法时在 `examples` 仓执行 `python -B tools/verify_gameplay_components.py --engine godot`，也可选择 `unity` 或 `cocos`。[运行器](../../../examples/tools/verify_gameplay_components.py)

目标是让新游戏用脚本和配置接入同一套玩家房主框架。验收用合作解谜、连续运动与现有赛车三类用例。编号沿用差距清单。进度与运行证据分别在[执行状态](执行状态.md)和[验收记录](验收/记录.md)维护。

## 范围和运行环境

| 范围 | 交付口径 |
|---|---|
| 首个可玩版本 | 第 1、2、3、5 项。三个前端接入第二个游戏，争抢、挂接、转权和第二种运动模型经真实房间传播 |
| 后续必须完成 | 第 4、6–13 项。各自独立验收；保留现有房间和协议回归 |
| 验收环境 | 按用户最新确认，只验本地。用回环接口测试发现和匹配，使用独立玩家进程验证续局。Steam 登录、平台匹配、双机公网均跳过 |
| 范围外 | 部署独立游戏服务器，复刻 Photon 私有服务端或完整确定性关节求解器 |

## 任务、契约和验收

| ID | 实现契约与改动位置 | 通过条件与参考 |
|---|---|---|
| 1 通用引擎入口 | core/session 组合现有房间和复制；三端开放注册模板、生成、提交、事件订阅与释放。公开参数使用 schema、对象、字段、玩家和代次 | 用相同配置接入解谜；场景脚本操作对象、读取回调，三端实际实例一致。[引擎接入](https://doc.photonengine.com/fusion-core/v3/integration/engine-binding) |
| 2 客户端权威策略 | ObjectAuthority 处理申请、持有人答复、释放和结果；校验连接、局、对象、代次、请求序号。策略覆盖房主指定、事务、动态争抢与冷却、离线销毁、随主迁移 | 两客人争同一件道具，只有一个生效；拒绝、超时、离开可见范围、旧包、掉线均可收敛。[所有权](https://doc.photonengine.com/fusion-core/v3/manual/ownership) |
| 3 对象身份与寿命 | 创建请求携带来源、请求号、模板和地图。预置对象按地图和稳定键识别；全局单例和子对象有独立身份；挂接验证父辈关系 | 并发生成幂等；换图后预置门对应；挂载装备、卸下、销毁父节点和重连后树一致。[创建](https://doc.photonengine.com/fusion-core/v3/manual/object-creation) |
| 4 多地图 | 房间发布带版本的活动地图表及增删事件，适配器报告加载完成，卸图按归属清理 | 同时加载两图、只卸一图，慢客户端及重入者最终一致。[场景](https://doc.photonengine.com/fusion-core/v3/manual/scene-management) |
| 5 任意模型预测 | 抽离车场消息与单实例调度；模型注册输入、恢复状态与单步；队列按对象和授权代次隔离 | 一人同时运行两种不同模型，暂扣下行、换权后重演无串流。[预测](https://doc.photonengine.com/fusion-core/v3/getting-started/modes-and-topologies) |
| 6 网络时钟 | 会话提供网络时间、对象采样时间、偏差、速率、RTT；适配器暴露同一单位 | 可控延迟、漂移、长暂停后收敛，三端倒计时读取同一截止时间。[时间](https://doc.photonengine.com/fusion-core/v3/manual/time) |
| 7 兴趣与频率 | AuthorityState 维护对象兴趣键、玩家订阅、对象发送倍率；进入完整基线，离开和销毁优先于限频 | 两区域和队伍交叉订阅；变更单个对象归类可见性即时更新；快慢对象包数可核对。[兴趣键](https://doc.photonengine.com/fusion-core/v3/manual/interest-area) |
| 8 RPC | 发送前按接收者可见性路由；可靠调用返回可关联的成功或失败，含对象消失、玩家离开、重试耗尽 | 抓取目标连接验证隐藏对象事件不外发，失败不堵塞后续可靠事件。[RPC](https://doc.photonengine.com/fusion-core/v3/manual/rpcs) |
| 9 编码 | 按兼容版本协商压缩整数、浮点量化、数组局部差量及字符串复用；以已确认基线为准 | 与原编码同负载对照字节数、误差；旧端、丢包、列表缩短和重连可解码。[序列化](https://doc.photonengine.com/fusion-core/v3/manual/serialization) |
| 10 刚体 Forecast | 三引擎分别绑定原生位姿、线角速度、睡眠和传送；区分远端物理代理和输入回放 | 实际物理节点碰墙、停住、传送和唤醒，记录权威与代理轨迹。[原版实测](../../research/fusion/findings/client-audit.md) |
| 11 入局策略 | RoomHost 可配置容量、进行中准入和旁观身份；现有车场默认 4 席锁局；晚加入需当前基线 | 第五人按配置入局；满员拒绝、旁观不能写、老票据复位正确。[连接与房间](https://doc.photonengine.com/fusion-core/v3/manual/connection) |
| 12 房主迁移 | 检查点带房间任期、成员、地图、对象、授权与输入进度；就绪候选人选举、端点切换及旧任期隔离 | 三个独立进程中杀掉房主，幸存者接续同局；过期房主不能重新写入。迁移期间单独记录可恢复点和状态损失。[Master 归属](https://doc.photonengine.com/fusion-core/v3/manual/ownership) |
| 13 发现与匹配 | 统一发现接口提供房间名、区域、属性、版本、余位、加入端点和身份来源 | 两房筛选、满员冲突、过期列表、断线重入。在本机回环接口验证，当前不要求 Steam。[匹配](https://doc.photonengine.com/fusion-core/v3/manual/connection) |

## 依赖与交付顺序

1. G0 建立基线，冻结增量协议边界。先沿现有拼图打通第 2 项，再将真实调用收进第 1 项，随后接第 3、5 项。G1 以三端解谜和双模型丢包回放签收。
2. G2 的第 4、6、7、8、9 项可分能力开发。地图依赖对象身份，RPC 可见性与限频依赖复制状态，编码验收使用固定对照输入。
3. G3 的第 10 和 11 项分别依赖通用引擎入口、场景基线；第 12 项依赖成员、对象、地图和状态恢复；第 13 项可先实现服务接口，再验证迁移后的端点更新。
4. G4 通过独立 Core 构建、三引擎 Release、真实三进程解谜、四人百对象故障测试和新增专项。记录实测环境、命令、退出码、恢复时间及摘要。各能力须同时具备运行入口和证据才计入完成数。

## 调度约束

协议先检测能力，再向兼容端发送增量消息。代码、契约与测试按能力一同落地。不同构建树可独立验证，使用同一 out/runs/current 的真实进程验收逐场串行。复用 tools/build.py 和现有构建目录。
