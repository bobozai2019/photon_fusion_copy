# Core 与可替换网络层改造方案

新游戏从 Godot、Cocos2d-x 或 Unity 开房即可使用纯 TCP。接入方拿到一份平台 SDK 和传输接口头文件后，可以用自己的 P2P 插件重跑同一个游戏。Core 独立构建，掌握房间、RPC、属性及发包前的内容整合。首轮交付与现有 SDK 一致，验收 Windows x64 Release。本文为拟实施方案，隔离工作树和已核实的基线见[执行状态](执行状态.md)。

## 从一次发送划分职责

| 位置 | 对一次发送负责的内容 | 交付物 |
| --- | --- | --- |
| `core/session`、`core/state` | 房间准入、局次、对象写权、RPC 路由与确认、属性基线及差量。按接收方可见性和版本选内容，决定顺序、通道、包预算，以及哪些状态可被后续版本覆盖。 | 独立的 `Netcode::Core` 静态库。Core 测试可接内存传输。 |
| Core 的统一发送出口 | 收齐一次发送周期里写给各对端的完整业务消息。房间控制可立即提交，普通状态按既有发送节奏提交。同一对端、同一通道的消息可一次提交多条，保留每条边界。 | 拟新增 `core/session/outbound.*`。先接入已有编码器，覆盖迁移与断开前待发的控制消息。 |
| `network/api`、`network/host` | 公共 C 头文件定义连接与消息投递接口。薄适配器把具体插件接到现有 C++ `Transport`，供平台或 C++ 应用组合。 | 可单独分发的头文件、宿主适配器。公开版本化入口；插件可静态注册或由宿主加载 DLL。 |
| `network/tcp`、`network/direct` | 建连、监听、收发、拆帧、积压、关闭和连接事件。纯 TCP 在 Windows 调用 Winsock，POSIX 移植复用系统 socket。已有 TCP＋UDP 直连单独保留。 | 独立 TCP 插件、兼容 Direct 插件。每个插件可用传输头文件独立构建，标准 TCP 路径无需引擎、Steam、账号或云服务。 |
| `engineplatform/{godot,cocos2dx,unity}` | 将脚本或宿主传入的配置交给适配器。每个会话选择一个实现。 | 三个独立平台包，随包带默认 TCP；为原有直连入口提供 Direct。游戏及演示素材继续归同级示例仓。 |

例如客人为对象改分并请求一个技能。Core 分别维护分数版本、写权代数和技能调用序号，为房主生成业务消息。TCP 插件写入长度与通道并处理部分写入，接收端还原完整消息后交回 Core。外部 P2P 若已有消息边界，可以直接交付相同的业务载荷。Core 的 RPC 回执与属性确认仍由对端业务协议推进。[传输接口草案](传输接口.md)

## 构建和外部接入

| 使用方式 | 输入 | 可见结果 |
| --- | --- | --- |
| 本地单独改 Core | C++ 工具链、传输接口定义、内存测试后端 | 只编译并安装 Core；空 CMake 工程只链接 `Netcode::Core` 即可驱动内存会话。 |
| 本地单独改网络 | 已安装的传输 C 头文件、系统 socket 或自研网络库 | TCP／自研插件各自生成一个 DLL，用同一消费者测试。拟给构建驱动新增独立的 `transport-tcp` 产品；与 SDK 产品一样，构建树和安装树按产品、配置隔离。 |
| 外部交付 | 已安装 Core、适配器、三端各自的引擎依赖、已构建的插件 | Godot 插件将 DLL 导出到 Player 可从磁盘加载的位置，Unity UPM 按平台将 DLL 放入原生插件目录，Cocos 把 DLL 随宿主部署。宿主通过配置解析插件路径，记录实际加载的版本。从空目录安装并导出一次，以覆盖编辑器与成品路径差异。 |

## 需求、范围和交付判据

| 范围 | 可观测结果 | 任务 |
| --- | --- | --- |
| MVP · 独立核心与内容整合 | Core 可单独编译、用内存链路跑房间；对指定对端可追踪一次提交包含的控制、RPC 和快照。兼容链路可比对每条消息的原始业务字节。 | T1、T3 |
| MVP · 默认纯 TCP | 两个离线 Windows 进程仅凭 IP 与端口开房、互调 RPC、复制属性和重连。TCP 数据连接不创建 UDP socket；局域网发现作为独立可选能力测试。 | T2、T4 |
| MVP · 外部替换 | 仓库外的小项目仅用已安装的 C 头文件和自己的网络实现编译 DLL。每种引擎的同一份已构建游戏或宿主分别用 TCP 和该 DLL 跑通。 | T1、T2、T4、T5 |
| MVP · 兼容与性能 | 原有地址／端口入口继续走 `direct`；旧版与候选版在该链路上双向互测。属性优化的既有评测矩阵继续生效。 | T3、T4、T5 |
| 后续可选 | 跨消息共用线上封套，按双端协商启用；Steam 插件接入与真实账号双端验收；其他操作系统打包。已有可选 Steam 功能随其现有构建接口单独回归。 | 取决于带宽测量、依赖与验收环境 |
| 另案 | 同一对局中途切换到不同传输、公共打洞或中继服务建设。 | 独立需求 |

这里区分两种“合包”。本轮交付 Core 按对端组批、一批内提交多条完整消息，并保留已有快照按预算合并字段的行为。若后续要把多条 RPC、房间消息、快照编码为**一条新的线上消息**，需协商协议能力、定义子消息长度和失败边界、在旧端回退为逐条发送。先测组批后的系统调用、有效载荷和排队延迟，再决定是否引入新格式。

## 实施顺序与可并行窗口

| 任务 | 前置与写入范围 | 实施顺序和完成判据 |
| --- | --- | --- |
| T0 · 工作树与基线 | 文档、基线指纹；集成前取得包含独立 SDK 的可引用提交 | 核实旧 HEAD、当前 SDK 和性能热区；记录后续集成 SHA、已安装包及其哈希。当前状态见[执行状态](执行状态.md)。 |
| T1 · 冻结传输边界 | 仅新增 `network/api`、独立测试工程 | 用 C 和 C++ 各编译一次头文件，验证 ABI 版本、缓冲区寿命、接收事件顺序和背压。固定客户端可加载独立构建的测试 DLL。 |
| T2 · TCP 和外部样例 | T1；新增 `network/tcp` 和安装包消费测试夹具 | 先验证纯 TCP 单连接，再验证一主多客、半包、粘包、慢读、连接被拒、断开及重连。外部示范插件使用独立实现和可辨认的运行标识。 |
| T3 · Core 发送出口与旧 Direct | T1、可复现 SDK 基线；`network/host`、`network/direct`、会话发送点 | 先用 Direct 适配原连接，再接入统一出口；分开提交以便逐步对照。检查逐对端顺序、排队失败和重试、可靠 RPC 去重、属性终值收敛、房主接替与旧端互通。 |
| T4 · 三端入口与打包 | T2、T3；各适配器及产品构建、安装入口 | 为每端加带 provider 的新开房／加入入口，接通同一工厂至重连与迁移。保留已有入口、CMake 目标及成品布局的兼容路径。从安装树构建平台，分别在干净外部项目导出或编译。 |
| T5 · 二进制替换与性能签收 | T4、性能线可复现基线；本工作树的验收结果 | 每端固定同一产品哈希后换链路；串行跑真实性能矩阵。保留双端包指纹、原始结果和失败格，再决定切换新项目默认值。 |

T1 和独立的 ABI、TCP、测试夹具工作可先在新工作树推进。T1 冻结后 T2 与 T3 可并行，T3 的现有源码接入以 T0 的 SDK 提交为输入。T4 可按引擎分开实施，用同一位集成人维护公共 CMake／打包入口。回退可按提交逆序撤回默认切换和平台接入；已发布 `0.1.0` 归档继续用于对照。

## 与属性性能优化并行

- 性能线维护属性访问、绑定缓存、变化掩码、ACK 与观察端回写。重点交叉文件是 `core/state/replication.*`、`core/state/snapshot_codec.*`、`core/session/script_game.*`、`engineplatform/godot/game.cpp`、`scene_replicator.gd` 和 `research/fusion/probes/property_*.py`。网络侧优先利用现有的 `Transport` 注入点和新文件。触及交叉文件时先取已落地的性能提交，在本分支做最小调用点接入，保留性能线的字段处理逻辑和计时位置。
- 主仓 `D:/photon_copy/netcode` 只作现场参考。候选编译树、安装前缀、发布槽、锁、测试日志全部放在网络 worktree 自己的 `out/`。示例侧使用独立副本及候选专用锁清单；Cocos 引擎显式给出源码路径，外部依赖只读复用或单独缓存，Unity 工程与 Godot 导入缓存各自独立。CPU 计分与主仓同机性能跑数错开时段，双端分配独立端口。
- 合并顺序为先取得双方认可的 SDK／性能基线 SHA，再在网络分支整合该提交，审核交叉文件差异，依次跑原 Direct、适配后的 Direct、纯 TCP，最后纳入主线。接入发生冲突时回到同一基线逐个重放调用点，用相同输入复测。全量复制主工作区会把采样实验混入候选版本。

## 验收与交付

| 关口 | 验收做法 |
| --- | --- |
| G1 · 契约和网络实现 | 对内存后端、TCP 和外部 DLL 跑一套收发契约。用受控短读、短写和小队列稳定触发边界；记录发送结果、事件顺序、两端字节和关闭原因。 |
| G2 · 兼容性 | 用固定业务输入，比对旧 Direct 与新适配层在传输边界的业务载荷、先后顺序和通道，规范化随机身份与时间。用锁定的旧房主＋新客人、新房主＋旧客人走原 Direct，覆盖入房、写权交接、可靠 RPC、快照终值与接回原席位。 |
| G3 · 发给外部的包 | 解压 Core 与各平台产物到仓库外。Godot 导出 Player、Unity 从 UPM 安装后导出 Player、Cocos 链接安装包编译宿主。相同引擎的两端均使用同款驱动。记录游戏／平台二进制 SHA、实际加载的 provider 标识，并分别用 TCP 和外部插件通过入房、八字段、双向 RPC、断线、重连。缺插件、ABI 版本不匹配均在开房阶段给出具体错误。 |
| G4 · 默认值与性能 | 在同机 Release 对比 A 已固定的性能基线＋旧 Direct、B 相同属性实现＋适配后 Direct、C 相同候选＋纯 TCP。A/B 识别拆分成本，B/C 观察链路差异。每格记录步率、步间隔 P95、停写前观察端看到的版本、终值收敛、排队峰值及最老包等待时间。 |

性能复用现有 15 格：1,000 至 5,000 字段共五档，静置、每 100 ms 轮换写 10%、每 100 ms 全写三类，每格每版本至少五个独立房间，写端、观察端分开计分。沿用性能线的逐格标准，包括各角色至少 48 步/秒且达同格 Fusion 的 80%，终值 100% 正确；变化版本的可见率、收敛时间仍须过原方案的全部门槛。锁定同批 Fusion 参考数据和同链路旧版数据。A 尚未达标的格单列为继承问题；B/C 新出现的倒退分别定位。新默认 TCP 的发布以其自身完整矩阵过线为准。旧 Direct 的成绩不能替代 TCP 的成绩。

验收在后续实现分支的 `task/transport-providers/验收/` 保留摘要与产物指纹，原始日志进入该工作树的 `out/`。现有 Core 消费、三端游戏消费和 Godot 性能探针可作为起点；候选包的显式输入、运行位置和验证顺序列在[执行状态](执行状态.md)。
