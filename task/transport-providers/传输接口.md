# 传输插件与 Core 消息边界

v1 的字段宽度、调用约定和返回值以[公共 C 头文件](../../network/api/netcode/transport_provider.h)为准。首轮二进制交付使用 Windows x64 DLL。C 夹具从安装后的头文件独立编译，C++ 宿主通过固定符号加载。

## 宿主如何使用插件

宿主从应用配置选定的插件加载固定 C 符号 `netcode_transport_get_api`。调用方传入请求的 ABI 主版本、输出表容量和输出地址；成功时表头给出 `abi_version:u32`、`struct_size:u32`、`provider_id` 与 `build_id`，后接函数指针。主版本必须匹配，结构尾部可扩展，所有必需函数都应在返回的有效长度内。标识是有长度的 UTF-8 字节串。只跨边界传固定宽度整数、指针、长度和不透明句柄；缓冲区由所属模块回收，插件在 C 入口内转换异常。静态注册使用同一表。

| 操作 | 主要输入 | 结果及所有权 |
| --- | --- | --- |
| `open` | `role:listen/connect`，目标端点字节及长度，插件私有配置字节及长度 | 返回插件拥有的实例句柄或初始化错误。监听实例可接多个 peer，连接完成由事件报告。 |
| `send_batch` | 句柄、`peer:u64`、逻辑通道、按顺序排列的 `{data, size:u32}` 和条数 | 返回状态与连续接受的条数。已接受前缀由插件持有或复制，调用返回后输入内存可复用。Core 仅重试剩余后缀。单消息发送等于长度为一的批次。 |
| `poll` | 句柄、单调微秒、单次事件预算、宿主的事件接收函数与上下文 | 在调用线程顺序交付 `Open / Message / Closed`。事件给出实例内 peer、通道、字节及长度或断开原因。接收字节在回调返回前有效。宿主串行调用同一实例，且需要在回调结束后再调用实例。 |
| `close_peer / destroy` | 句柄、指定 peer 或实例 | `close_peer` 终止指定连接；失联或远端关闭同样报告原因。宿主释放所有实例后再卸载模块，`destroy` 返回后所有回调结束。 |
| `get_caps / get_stats` | 句柄，peer 为 0 时统计整个实例 | 能力给出每通道可接受的最大业务载荷和可靠有序支持。统计按通道记录完整业务载荷的收发字节、待发字节、峰值与最长待发时间。收发总量包含已断开的 peer。旧接口里的 TCP／UDP 计数在兼容层映射。 |

`ok` 表示本地已接受整批。`would_block` 返回可为零的已接受前缀。其他错误的接受条数为零，包括载荷超长、参数错误和连接关闭。加载方分别处理不支持的主版本和过短的 API 表。成功连接按 Open → 零至多条 Message → 一次 Closed 的顺序投递。异步连接失败允许只收到一次 Closed。peer 为连接实例内的非零临时标识，新连接使用新标识，房间玩家身份与接回凭证由 Core 分配。

## 通道、组批和确认

- `Control` 承诺可靠有序，`Game` 允许尽力投递。纯 TCP 对两者均可靠有序，独立编码通道标志，接收端仍能识别业务类别。旧 Direct 保留 TCP 控制、UDP 游戏及关联和心跳过程。v1 沿用每条控制载荷 65,535 字节、游戏载荷 1,176 字节的协议上限，插件提供相应的逻辑承载能力；能力不足在开局前报错。
- Core 的发送出口维护接收方、通道和该通道内的提交顺序。兼容模式按旧发送顺序切成连续批次；保留房间控制即时刷出、断开前排空及按原时点发送状态的行为。插件按有界工作量推进网络，慢客人的队列独立于其他连接。
- RPC 可靠投递当前含序号、确认、重传和去重，部分控制消息影响其后游戏包的可见性。插件保留每条消息边界。Core 只合并语义上可替代、尚未提交的状态；基线、收权、销毁、可靠 RPC 及其回执维持协议顺序和重试资格。队列满时分别记录已准备、本地已接受、对端已确认，按最后成功接受的位置继续。拆出口时尤其核对 `AuthorityState::packets` 生成阶段前移的发送记录，以及 `Rpc::transmit` 已分配的序号。
- TCP 插件在流上写入长度和消息类别，接收时先验证上限，再积累到完整帧。部分读写、一次收多帧和阻塞后继续由插件处理。已经写入 TCP 的旧帧可能阻挡更新帧；P95 排队延迟和最老待发消息年龄需进入 A/B/C 报告。若增加线上合包，另行冻结双端的功能协商与回退用例，已有 Direct 线协议作为兼容样本。

## 建房、发现与迁移

新入口使用 `Endpoint { provider_id, address_bytes }`；TCP 驱动解析 IP 和端口，P2P 驱动解释自己的对端标识。旧地址／端口签名映射到 `direct`，新建项目模板默认 `tcp`；指定 provider 缺失时报告该标识。房间列表与邀请可携带可公开的端点描述，本地认证配置随实例传入。

首次连接、接回原席位、备用房主监听和客人改连统一调用同一 provider 工厂。现代码 `StandbyEndpoint` 和 `add_standby` 要求非空地址及非零端口，LAN 列表还在编码里写入端口。迁移时为旧 Direct 保留旧列表与端点解释，为新 provider 提供带类型的端点与对应目录适配。`RoomDirectory` 作为可选发现服务；直接连接已知地址不要求部署目录服务。由 Core 决定入房、满员、锁房、接回凭证与接任资格，由驱动报告链路状态。

## 二进制兼容验证

用两份独立编译的插件在相同平台产物上轮换，保存 ABI 版本、provider 标识、宿主与插件 SHA-256。覆盖老宿主读取兼容表、主版本错误、必需函数缺失、短表、实例销毁、受限队列只接受部分条目、关闭后迟到事件。保留一个旧版业务包样本和可复现的原版直连程序，用于验证 Direct 的真实互通。
